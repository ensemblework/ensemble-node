# 05 · UI and UX

Chat-first teammates with familiar messenger navigation. Ensemble's flavour is Satin Gold on a near-black petrol night, the Woven Chorus mark, Figtree, and Ensemble's own cards (tasks, runs, approvals).

## Principles

- **Chat first.** Every screen leads back to a conversation. The composer is the biggest control on the page.
- **Recognisable signatures.** Nodes keep their own signature faces, with saved shapes, colours and eyes, independently of the model they use. They blink and breathe while thinking; reduced motion keeps them still. Model pickers and agent runs use the actual vendor or agent's mark.
- **What needs you is never buried.** Approvals are owner-only cards in the conversation, mirrored in the Activity panel with a badge.
- **Privacy you can see.** Anything only you can see is marked with a lock and the private (violet) tint: a room's My crew and what is in it, drafts, approval cards, error notices, run cards in shared rooms.
- **Honest status.** "Thinking…", the reply being written, tool chips and run states come from the server, never from timers.

The sidebar is one recent list across direct chats, crews and rooms, sorted by the newest message, including pending sends. Helpers' rooms are not in it ([Helper threads](#helper-threads)). All / Unread / Groups and Search chats narrow it without changing server data. Each row keeps its timestamp, preview, typing or private indicator, and unread count. Refused sends are marked Not sent. A DM tooltip names its node and handle. New conversation and full message search sit at the top; Needs me, Routines, Sessions, Invites, Connections and account settings sit below. The Needs me badge counts what Ensemble's does plus the nodes' cards; phones retain an attention dot on back-to-chats. Live changes update the preview immediately, not after a bootstrap refetch.

On desktop Collapse conversations becomes a 68 px rail with recent signatures and navigation; Expand restores the 304 px list. `node.sidebar-collapsed` remembers the choice in this browser. The Activity panel is closed initially; its own toggle and `node.activity-open` preference restore it when wanted. Neither preference contains conversation content.

## Model and agent marks

`components/model-logo.tsx` and `lib/model-brand.ts` resolve the actual model first, then a known provider/agent when no model identifies the maker. GPT/Codex, Claude, Gemini, Grok, GitHub Copilot, Cursor and the other supported vendors use local canonical SVGs, shared with the Hub. Model pickers and run cards use these marks; source group icons do not stand in for a model. Node identities in chat headers, messages, sidebars, search results, mentions, settings and node selectors always use `NodeAvatar`, not the model mark.

`public/providers/manifest.json` and `NOTICE.txt` retain provenance and identification-only trademark notices. The Grok SVG is from LobeHub/lobe-icons under its included MIT licence. A public node exposes no private model choice: its signature face uses only its public avatar, never an inferred model.

## Connector logos

`ConnectorLogo` and `lib/connector-logos.ts` are the shared brand renderer and resolver. Connections use the catalog API's `logo` key (falling back to its ID for older responses), not the display name. Native connector tools and catalog MCP tool names use the same assets in completed replies, live tool chips and approval cards. Generic Ensemble tools stay generic; `apps_search` does not identify a service, so it keeps its wrench. Custom MCP names, including ones named after a vendor, are never treated as proof of that vendor's identity.

Assets are local under `public/connectors/`, reused from Ensemble's brand library with per-image provenance in `manifest.json` and licences/trademark attribution in `NOTICE.txt`. Wispr Flow and Zotero use real vendor marks rather than the Hub library's older placeholder lettermarks. This does not add integrations: the API catalog still controls what can be connected.

Tiles have fixed dimensions and contained, unmodified aspect ratios. A neutral white backing keeps black and coloured marks readable in both themes; small chat marks use 16 px tiles and connection rows use 36 px. Adjacent connection names make row logos decorative; standalone/tool logos have accessible names. Unknown logos use initials, custom MCP and CSV use explicit generic icons, and failed image loads retain the same tile with an accessible "logo unavailable" fallback. Branding does not replace connection status text, approval controls or tool-failure indicators.

## The model picker

One picker everywhere a model is chosen: new nodes, new nodes in a crew, and the node's settings. Groups: **Included with Ensemble** (Everyday and Step-up, with relative credits), **Your API keys** (per provider), **Your AI plans on ‹computer›**. The bootstrap carries the included models, so the picker opens at once; own keys and AI plans come from `/api/node/models` when it opens. A filter box appears for long lists, and the server's problems show at the bottom.

## Attachments

Both composers (a conversation's and the start page's) take files (`components/chat/attachments.tsx`, rules in `lib/attachments.ts`):

- **Adding:** the paperclip opens **Upload from this computer** and **Choose from Files**. Files can also be dropped on the composer (it shows "Drop to attach" while files are held over it; a file dropped elsewhere on the page is ignored, so the draft is never lost) or pasted. A picture that comes with copied rich text (the clipboard also has HTML with text in it, or RTF, as Word, Excel and web pages add) is ignored; a pasted screenshot is named "Pasted image ‹date› ‹time›".
- **Upload:** a file from the computer goes to the person's Ensemble Files at once (`POST /api/documents`, `summarize: false`) with real progress, before the message is sent. A file larger than the server keeps (`usage.maxFileBytes` from `GET /api/documents`: 25 MB on the hosted plan) is refused before it is read; any other refusal (a program, an empty file, quota) shows the server's own words.
- **Choose from Files:** the person's Files, newest first, searchable by name (`GET /api/documents?q=`). Each row shows kind, size and the date and time it was added, so files with the same name can be told apart. Picking one attaches it without uploading again; picking it again takes it off.
- **The shelf** above the text box has a chip per file: a thumbnail for pictures from the computer (a local preview), name, size, and while uploading the percentage, a progress bar and **Cancel**. Ready files have **Remove** (the file stays in Files). A failed upload shows why, with **Retry** and **Remove**. Up to 8 files per message; the same file is not added twice; a note says what was left out.
- **Sending** waits while a file uploads or after one failed, and says so next to the paperclip. A message may be files only. The paperclip's hint says who can read them: in a DM or crew, the nodes read the text of documents and see pictures when their model reads images; in a room with other people, nodes read files only from their own owner's messages, and others see a file's name but cannot open it.

## Messages and cards

- **Your messages** sit on the right in a gold-tinted bubble; private ones are violet (outside My crew, with a lock and "only you and your nodes").
- **Node messages** sit on the left with the node's signature face and name; someone else's node retains its owner label. Repeated handles are omitted from message headers. Markdown subset: headings, lists, code, quotes, bold, links (bare and `[label](address)`) and GFM tables; known `@handles` are highlighted. Tables have column headers, aligned cells and the same inline formatting and safe links as other message text. Escaped pipes stay in cells; wide tables scroll sideways in a keyboard-focusable region without widening the conversation. Raw HTML stays text.
- **Records by title.** A node names Ensemble records by title, never by id (`lib/entity-text.ts`, the same rules as Ensemble's [docs/11 §4.1](https://github.com/ensemblework/ensemble/blob/main/docs/11_HOW_THE_ASSISTANT_WORKS.md#41-records-by-title-ids-for-machines)). A record link (`[@Draft brief](ensemble://task/…)`) shows its label and opens the record in Ensemble; a room opens here. A bare id of a record the message names (its `data.refs` and its tool chips' `refs`) shows as that record's title, linked; records with the same title get their kind, due date or a number. An id or record link in brackets right after the record's own title ("Expire Needs Me requests when their task ends (ensemble://task/…)") turns those words into the link, whether they are the whole title or its first clause; the title is never shown twice. On cards (briefs, reports), a record link nobody named shows as its kind, linked ("(task)"). Unknown ids, code, quotes and links stay as written, ids stay when someone in the turn asked for them (`data.showIds`), and what people write is never changed. Conversation previews, pins, reply quotes and Copy read the same way (`readableBody`). Text being written holds back a half-written id, using the turn's `refs` frame and its tool calls.
- **Code blocks** show the fence's language and a copy button above the code, which scrolls sideways instead of wrapping, also on a phone (`components/chat/code-block.tsx`).
- **Message actions** appear on hover or focus, or after a long press on a phone: react (the eight reactions), reply, copy, pin or unpin (only messages everyone in the room can read), delete (your own). Reactions show under the message with counts; yours are highlighted and the tooltip names who reacted.
- **Replies** quote the original above the message; the quote goes to it. A reply to a private message is private too. In a room's Room, replying with **Ask my nodes** asks your nodes about that message privately, quoting it.
- **Deleted messages** read "Message deleted".
- **Files on a message** (`components/chat/file-chips.tsx`) sit under its words as chips with kind, name and size. Your own link to the file in Ensemble's Files (`/files/:id`, new tab), and your pictures show a thumbnail read with your session (`GET /api/documents/:id/original`) once the chip is near the screen. Someone else's show only the name, kind and size with a lock; the tooltip says only that person can open it and your nodes see its name only. A message with only files previews as "📎 name" or "📎 3 files" in lists, pins and quotes.
- **Media in a message** (`data.media`: a node's reply, a plan's report, an approved draft, a shared message): pictures in a grid, videos in a player, other files as downloads, in the same gallery as [evidence](#evidence), on a phone as on a computer. Each piece is read through its message, which is how others in a room may open it. A message with only media previews as "📎 2 pictures, 1 video".
- **Shared to the room:** a copy shared from someone's My crew says so over its words ("Shared from Mira's crew", "Shared by Mira" when their lead posted it, "· @scout's reply" when it was another node's words); on your own, the line goes back to where it came from. The private original says "Shared to room", which goes to the copy.
- **Not sent:** a message the server refused stays with its reason, **Retry** (the same words, files and clientId, so nothing is uploaded again and the server keeps one copy) and **Edit** (back into the composer with its files, and its reply when that message is loaded).
- **Tools a reply used** fold into one line under it, "Used 4 tools · Search tasks, Read page, Assign to agent +1 · 1 failed", which opens into the tool chips: what the node did in Ensemble ("Create tasks · Added “Draft brief”."), each linking to the item in the Hub. A reply that used one tool shows that chip alone. They are shown only where nobody else reads.
- **Approval card** (owner-only; its words are in `lib/cards.ts`, the same in Needs me): "@node wants to do this for you" with each held call as Ensemble describes it, by record titles, keeping its line breaks (pick some with checkboxes when there are several) → Approve / Discard; "@node wants to start work on your computer" with the agent, place and message → Start it / Discard; "@node wants to hand a session to @designer" with which session and its note (`action: "hand_over"`: no prompt or title) → Hand it over / Discard, then "Handed over" and "@designer manages this session now."; or "Post this in “Launch” for you?" with an editable draft → Post / Discard ("Post this answer…" when it answers someone). States: Waiting for you, Applying…, Approved, Partly applied, Posted, Discarded; errors keep the card pending.
- **Secret card** (owner-only, also in Needs me and the Hub's Needs me; `components/secret-box.tsx`, words in `lib/secret.ts`): "@node needs a secret: NAME" with why, a password box ("Paste NAME"), **Only send it to** (optional origins, filled with what the node suggested), a line on how the value travels, Save to ‹computer› and Decline. The line is accurate for each case:
  - The computer has a key: "Encrypted in this browser for ‹computer›: only ‹computer› can read it, and Ensemble's server passes it on without being able to. Key 7F98 5267 E5FD 5A05: it should match `ensemble secrets fingerprint` on ‹computer›." The fingerprint is worked out in the browser from the key it encrypts for.
  - An older computer: "Sent over HTTPS to Ensemble's server, which passes it to ‹computer› without keeping it. ‹computer› is too old for end-to-end encryption; update Ensemble there."
  - Its key changed: "‹computer› now reports a different key from the one it was paired with, so nothing is sent to it. Pair it again (`ensemble login`), then type the value again." The box is disabled.
  - Then what happens to it: with destinations, "Kept encrypted on ‹computer› for use by reference only: runs there send it to ‹origins› without seeing it, and it is never put in a run's environment"; without, "Kept encrypted on ‹computer›; runs there that may have it get it as $NAME".

  The value is sent once and never shown again; the card then reads "Saved on ‹computer›. Runs there get it as $NAME." (or "use it by reference only, sent to ‹origins›"), with "Encrypted end to end." or "Sent over HTTPS through Ensemble's server (not end to end)." Errors (computer offline, no answer, a refused box) keep the box open. Settings → Computers shows each computer's **Secret key** fingerprint, or that it changed, or that secrets go over HTTPS only.
- **Node proposal card** (owner-only, `data.type: "node_proposal"`): with new nodes and crews on Ask me first, a node proposes one: "@lead proposes a new node" with its name, role and charter (Show its charter), or "@lead proposes a crew" with its name, nodes and lead → **Make it** / Discard. Made, it links to the new node's chat or the crew.
- **Plan card** (`components/chat/plan-card.tsx`, rules in `lib/plan.ts`): a lead's plan for its crew, as Ensemble projects its mission. Its opening words, "Plan" with its status and Stop (only while it runs, after a confirm), the goal and its facts, then the requirements ledger and one row per step. A routine's run (`data.routine`) has a small chip in its header, "Routine · Morning summary", which opens the routine in Routines; its card is not in the chat ([Routines](#routines)).
  - **Status:** "2 of 4 done" while it runs, then Planning, Reporting, Succeeded, Partly done, Failed or Stopped. A plan from before outcomes that ended "done" still reads Done.
  - **Facts** (its `constraints`, rules in `lib/plan-facts.ts`), on one line under the goal: where ("In ensemble on Laptop"), the branch, what it publishes (Nothing committed, Commits, never pushes, Pushes, Opens a pull request) and how its builds share the folder:

    | `parallel` (and `integrate`) | Words |
    | --- | --- |
    | `serial` (the default, for a plan with a folder) | One at a time in the checkout |
    | `worktrees` (`merge`, the default) | Each build in its own worktree, then merged |
    | `worktrees` with `rebase` | Each build in its own worktree, then rebased |
    | `worktrees` with `patch`, or publishing nothing | Each build in its own worktree, then applied as patches |
    | `snapshots` | Each build in its own copy, then applied as patches |
  - **Requirements:** each requirement the owner asked for, with Open, In progress, Accepted, Failed, Deferred or Cancelled, and a line such as "3 of 5 accepted · 1 failed". Show criteria lists their acceptance criteria (optional ones marked). Deferred ones say why.
  - **A step's row:** the node's face and handle, the step's kind and who does it ("Verify · agent session", "Write · on its own"), whether it ran (Waiting, Working, Done, Blocked, Skipped, Stopped, or Finished when it has a verdict) and what came of it (Pass, Fail, Blocked, Unverified), the brief on one line, and the report or the live progress. A waiting step that an earlier failed, blocked or unverified step holds reads **Held**, "held by @builder" (Ensemble names that step by its id; the card shows its handle, and works it out from the steps before when the id is not on the card); otherwise "after @builder". A repeat shows "Attempt 2 · repair" or "Attempt 2 · retest". The row also counts its agent runs and evidence. A step waiting for its place on the computer (a checkout or worktree another step holds) shows Ensemble's own words, "Waiting for @builder's step to finish with live-test.".
  - **Parallel work** (§8.15): an integration step (`integrates`) says "Brings in @builder's and @designer's work", each linked to its step on the card. A check whose pass a later change in the same place no longer covers (`staleAfter`, with `tested`: what the pass was for; older cards work it out from the attempts) has an amber note: "Passed for 1a2b3c4, but @designer's step then changed it (9f8e7d6): this pass doesn't cover that change." Nothing waits because of it.
  - **Open, a step shows** its whole brief (record links by kind), the requirements it covers (linked to the ledger), the settings it asked for, its report, its attempts (each with outcome, its checks with verdict and detail, and what it built or tested: "built 1a2b3c4 on feature-x", "tested 1a2b3c4"), its [evidence](#evidence) and the agent runs it started, each a run card. Those run cards are not in the timeline, the conversation's preview or its unread count. Opening a step reads the plan with all its run cards (`GET /api/node/plans/:id`), so runs from earlier pages, and a helper's runs in its own room, are there too.
  - **A helper's step** (`executor: "helper"`) reads "Helper · Alpha" and, open, has the helper's thread ([Helper threads](#helper-threads)).
  - **Work card:** a node's own piece of work (`kind: "self"`, one step) is one compact block: "Work", its kind and status, the title, the live progress or result, and Details with the brief, attempts, evidence and runs.
- **Run card** (`components/chat/run-card.tsx`): a run on your computer, shown like a coding agent's own app. A run in an agent session is that session's card.
  - **Status line:** title (an update to a run reads "Update: ‹title›"), status pill and, while it runs outside a session, **Stop** (after a confirm; only for the person whose computer runs it). Under it the engine (Claude Code, Codex, Cursor, GitHub Copilot and Ensemble's other engines, or Ensemble's agent; before the job is read, the session's agent), the model, the thinking level, the computer, the time so far (ticking while it runs) and the attempt when it is a repeat. Then the latest progress line, or for a run the node queued in a session "it starts when the run before it ends", or for one a newer message took over (pill Updated, Replaced or Stopped) what happened to it.
  - **What the agent was told** (`data.told`): a run Ensemble started straight from a plan step has the packet it compiled for the agent (Goal, Your part, Constraints, Inputs, Who you are, Report), folded under the status line and shown with its parts as small labels. On the run going on in a session it is the session's own "What it was told" instead, so it shows once. A run that is Ensemble asking the agent once for the result it did not report (`data.reportAsked`) reads **Asked for its result**.
  - **Settings** (`data.settings`, `components/chat/session.tsx`): "Settings · as asked", "not as asked" or "not reported by the engine" opens what was **requested**, what was **resolved** (sent to the engine) and what the engine **observed** (reported), side by side; a setting that changed on the way is marked. A table on wider screens, one block per setting on phones.
  - **Session** (`data.session`, only on the run going on): the session's status (Working, Needs you, Queued, Idle: Ensemble's words for it), who manages it ("Managed by @builder": its `nodeId`, which can change), "Now:" what it is doing (with "What it was told": the card's packet when it has one, else the session's prompt), where it runs, and its queue in order. A card's `data.session.agent` is the agent's name and `agentId` its id; `GET /api/node/sessions/:id` has its id in `agent` and its name in `agentName` (`sessionAgent` in `lib/session.ts`): names are shown, ids decide. For the session's owner: Move earlier, Move later and Cancel on each queued message, and **Steer…**, **Queue…**, **Stop and send…** and **Stop** (keep or drop the queue). They act at once, through the same code as the node's own session tools, so the node always knows. Edits show at once; when Ensemble refuses one, the queue goes back and its words show in the card. A queued run says its place in line and can be cancelled.
  - **Hand to…** (the session's owner): a list of their other lasting nodes (never a helper, nor the node that has it) → **Hand it over** (`POST /api/node/sessions/:id/hand-over`). The node it goes to sees what the session did, sends it messages and answers for it; runs already started still report to the node that started them. Then a note says "@designer manages this session now." and the card reads it again. A session no node manages (started in the Hub or the CLI) says so, has no controls (Ensemble refuses them) and offers **Give to…** instead; the Sessions page lists those too. Once a session's runs have all ended, its newest card in the conversation keeps a short session line: its state, who manages it and Hand to….
  - **Needs you:** the run's own cards from Ensemble's Needs me (`detail.jobId` is this run) and its run approvals, one at a time ("1 of 2"). A permission shows its command with Allow once and Deny, plus Allow for this run when the run is not on a paired computer (a paired computer takes answers from the web once only, and a push is confirmed each time). A question shows its options with the recommended one marked, a box for your own answer when the agent allows one, and "Skip, let the agent decide". Risky ones ask to confirm first; ones that only that computer may approve offer Deny here. The same answers work on the Needs me page (`components/decision-answer.tsx`). "Answer it in Needs me" shows only when the run waits on something not listed here.
  - **Work log:** "Working · 23 tool calls" (or "Worked for 4m 20s") opens the engine's trace (`components/chat/work-log.tsx`, `lib/work-log.ts`). Consecutive tool calls fold into one line ("Read 1 file, ran 2 commands, edited 1 file") with their time and failures; the group the run is working in stays open. Each call has an icon for its kind (command, edit, read, search, web, MCP tool, question, subagent, thinking), its command in monospace or its target, its duration, and a red mark when it failed; it opens to the command (with copy), the lines removed and added, the input and the output. Thinking stays folded to its first line. The engine's own messages and milestones (asked you, restarted, decided on its own) sit between groups. The newest 12 items show first; "Show earlier" adds 30 at a time.
  - **Report** (`data.report`): what the worker reported, in a block of its own: Report with its outcome (Done, Pass, Fail, Blocked and why), "2 of 3 checks passed · 1 failed", each check with its verdict and detail, the commit it built or tested, and links it gave. A run with a report shows it instead of the free summary.
  - Then its [evidence](#evidence), the files the run changed with +/− counts, the summary (Markdown) or the error, and "Open the task in Ensemble" for a run on a board task (work a node runs on its own has no board task).
- **System lines** (joined, left, brakes, the line a room got when it moved to Room and My crew, "Mira chose not to share that.") are centred and muted.

### Evidence

Files a run attached (`data.evidence` on its run card: screenshots, videos, traces, reports, logs) show as a gallery (`components/chat/evidence.tsx`, rules in `lib/evidence.ts`) on the run card, and on its plan step, which gathers its runs' evidence. A node's media (`data.media`) uses the same gallery in its message.

- **Pictures** (PNG, JPEG, GIF, WebP, AVIF) show as thumbnails read with your session (`GET /api/node/evidence/:id`; media in a message through it, `?message=<id>`) once they are near the screen, and only when the bytes that come back are such a picture. They open in a lightbox: the picture large, its caption, "2 of 5", Download and Close. Arrow keys move, Home and End go to the first and last, Escape closes and focus goes back to the thumbnail; on a phone a swipe moves.
- **Videos** play in a player with its controls in place, showing a first frame until played (and larger in the lightbox). One that cannot be read becomes a download.
- **Everything else**, and every active format whatever its kind says (HTML, SVG, XML, scripts, PDF), is a download row with kind, size and caption. Nothing active is ever shown in the page.
- A caption shows under each piece, and "For: ‹requirement›" when it is for one of the plan's requirements, linked to the ledger.

### Helper threads

A helper's room (`kind: "task"`) is not in the conversation list (`lib/threads.ts`). A helper's task is a step of its parent's plan. Under the message that asked for the work, a chip reads "@scout, helper of @lead · working · 4 messages" (or quiet). It opens in place to the helper's conversation, read only: the brief its parent wrote (**Brief**), what it is writing now, and its report (**Report · Done**, Pass, Fail or Blocked), with "Open the helper's room". Its parent tells you once, when all its helpers have reported. Reading it there marks the room read. A link to a helper's room still opens it, read only.

- **Where it shows.** Ensemble's room view says whose helper it is and where (`helper`: the parent, the helper, the origin room, whether it was asked privately, the message that asked, `originMessageId`, and the plan card its step is in, `planId`). The thread goes under that message, whoever wrote it; when it is not loaded, under that plan card; and the plan card's step for the helper has it too. Rooms from before these marks go under the parent's reply whose `node_helper` call names the helper or its room, or, read from their members, to the parent's direct chat. A helper none of these places is under Helpers in the "Working on" strip and opens in a side panel.
- **Asked privately.** A helper asked for in your My crew (`originPrivate`) shows only under a private message or card, and its chip carries the lock and the private tint, here and in the strip.
- **What it may do.** The thread's header says it: "Can read", "Can run sessions" or "Can use the computer" (the helper's `autonomy.grant`), and that it reports to its parent. The helper's room settings say the same.
- **Keep as a node.** In the thread's header and the room's settings, after "Keep @scout as a lasting node? It gets its own chat." (`POST /api/node/nodes/:id/promote`). The helper leaves its parent, keeps its charter and memories, and its own chat appears in the list. The thread then reads "Kept as a node" with "Open its chat"; its room stays as history, and deleting that room leaves the node.

### Working on

Under a conversation's header, a one-line strip lists what is working there, from what is already loaded: your live plans and pieces of work ("2 of 6 done", the work's progress), routines' runs that report here, your agent sessions with a live run, one per session ("Running · 2 queued"), and helpers that are working. A chip opens its card in the timeline; a routine's run, whose card is not in the timeline, opens its card in a side panel. Quiet helpers whose message is not on screen follow under Helpers. The strip scrolls sideways on a phone and is gone when nothing runs.

### Stopping work

While your work runs in a conversation (a live plan or work card, a live agent run, or a reply being written), its header has **Stop**; More always has "Stop this conversation's work". Both, and the composer's stop button while a node writes, call `POST /api/node/rooms/:id/stop`, which stops your nodes' replies, plans and their runs there. They ask first only when plans or runs are going on; stopping a reply being written does not ask. The result shows in a note ("Stopped. What was changed so far stays." or "Nothing was running here."). A plan or work card has its own Stop while it runs (`POST /api/node/plans/:id/stop`, after a confirm), and a session's Stop keeps or drops its queue.

## Rooms with other people

A room with other people follows rooms v2 (Ensemble's [docs/35 §12](https://github.com/ensemblework/ensemble/blob/main/docs/35_ENSEMBLE_NODE.md#12-rooms-with-people)). The website's side is `components/chat/room-view.tsx`, `room-cards.tsx` and `room-people.tsx`, with rules in `lib/rooms.ts`, `lib/trust.ts` and `lib/cards.ts`.

| Tab | Who reads it | What is in it |
| --- | --- | --- |
| **Room** | Everyone in the room | What people send to everyone, leads' answers, shared copies, request cards, status cards, system lines |
| **My crew** | You and your own nodes | What you ask your nodes and their answers, your plan and run cards, your cards to decide (requests for you, questions about sharing, drafts, proposals) |

- **Unread per tab.** Each tab counts its own unread on its tab; a tab opens at its first unread. What each tab has shown is kept in this browser; the room's one read marker (on the server) moves only past what both tabs have shown. A message link, a search result or a card's button opens the tab it is in.
- **Who answers.** A message that names no node wakes nobody. Only a lead answers in the Room, and only when someone names it; naming someone's other node goes to their lead; your own other nodes answer you in My crew. Nodes' messages wake nobody. The empty tabs, the composer's choice and each node in the @ list say this briefly ("your lead: answers in the Room", "Ben's node: their lead answers").
- **The composer.** In the Room: **Send to everyone** (the default) or **Ask my nodes**, which sends privately to your lead (or the node you name) and opens My crew, where its answer comes; replying to a Room message this way quotes it. In My crew everything is private ("Only you and your nodes"). Each tab keeps its own unsent text. The handshake button asks someone something (below).
- **`@leads status`** as the whole message (punctuation allowed) is said as you type it: "Ensemble answers with everyone's status card. No node is woken." The answer is a **status card** per person, built by code: presence (online, away, offline), away until when and their note, and their missions and tasks for this room at the detail they chose (titles, or with requirements and steps), or that they ask first or share nothing.
- **Share to room.** On your private messages and your own nodes' private replies in My crew, the message actions offer Share to room: **As me** or **Through @lead** (`POST /api/node/messages/:id/share`). The copy goes to the Room; the original says "Shared to room".
- **Requests** ("Ask someone here…": the composer's handshake, More, or the room's settings): to one person, a Question, Share, Review or Work, with what you need; a review names its exact candidate (a commit with its repository, or a web address), and work may. Their lead answers questions and shares within their rules; reviews and work wait for their yes. The public **request card** shows who asked whom, the kind, its state (Open, Waiting for Ben, Accepted by Ben, Answered, Declined, Done with its outcome and requirements, Cancelled), the answer, and **Cancel request** for the person who asked while it is undecided. The person asked has **Decide in My crew**, which opens their own card: who asks for what, the candidate, which of their nodes would do it and what it costs, with **Accept**, **Edit** (accept as edited), **Decline** with a note, and "Always accept reviews from Ben in this room". The cards change in place (`node.message.updated`); the list is read again on `node.request`.
- **Questions about sharing** (disclosure cards, owner-only): "May @lead share this with the room?" with who asked what and what it would share → **Allow** / **Don't share**. Allowed, the lead writes the answer as the usual "Post this answer… for you?" draft; "See it in the room" once posted. Not shared, the room gets only "Mira chose not to share that.". A question to answer in the lead's own words (it uses your credits) reads **Answer** / **Don't answer**.
- **Away.** In the room's settings, "Set away": until you are back, for an hour, until 18:00, until tomorrow at 09:00 or until a time you pick, with a note (`PUT /api/node/rooms/:id/status`); **I am back** ends it. Everyone's presence shows as a dot beside their name in the room's settings, with their away line, read again each minute while the settings are open.

**What your lead may share** (More, or the room's settings) is a sheet of your own rules for this room (`GET/PUT /api/node/rooms/:id/trust`): for everyone here, and for one person over that (Change, and a reset to everyone's). Only what changed is sent, on Save.

| Setting | Choices (default first) |
| --- | --- |
| Status questions | Answer from my status card · Ask me first |
| How much of my status | Titles · Nothing · Details |
| Items in the room's shared space | Share them · Ask me first |
| Anything else of mine | Ask me first · Never |
| Answers in its own words | Allow · Ask me first |
| Requests for work and reviews | Ask me · Accept on its own (with which: reviews, work) |
| Monthly budget | Credits a month for answers in its own words; empty for no limit, with what was used this month |

Under it, **Items it may share here**: pages, tasks and files of yours your lead may read out in this room without asking (`GET/PUT /api/node/rooms/:id/shareable`), found by name and taken back with ✕.

## Routines

A routine is work a node does on its own: on a schedule, when tasks or pages change in Ensemble, or when a webhook calls (Ensemble's [docs/35 §6.5](https://github.com/ensemblework/ensemble/blob/main/docs/35_ENSEMBLE_NODE.md#65-routines)). `/routines` lists them all by node (`components/routines.tsx`, rules in `lib/routines.ts`), from the sidebar and Settings; a node's settings list its own, with New routine for that node.

**The form** opens in a drawer (in a node's settings, in place) and fits a 390 px phone:

| Field | What it takes |
| --- | --- |
| Title | Up to 120 characters |
| Node | One of your nodes, never a helper. A routine's node does not change once it is made |
| Reports in | The node's chat (the default) or one of your crews it is in: only where you read alone |
| What it does | **Instruction** (the default): work the node does itself. **Saved plan (advanced)**: a plan as a lead makes one (`node_plan`: goal, requirements, constraints, steps), as JSON, run as a plan in the node's crew |
| When | **Schedule**: every day at, weekdays at, every week on ‹day› at, every month on ‹day› at, every hour at :mm, or a custom cron, in a time zone (the browser's by default; search by city or region). **Event**: a task or a page changing, only for the actions ticked (task: created, updated, moved, assigned, deleted, agent run; page: created, saved, deleted; none ticked: any change), in your own space or one you name, gathered for 60 seconds by default. **Webhook**: its own address and token |
| Tell me | Always post the result · Only when something needs me · Never post (keep a log) |

- **Schedules.** A preset becomes a five-field cron in the browser and reads back before saving ("Every Friday at 16:30 (Europe/London) · 30 16 * * 5"); once saved, the list shows Ensemble's own words for it. A cron that is one of the presets opens as that preset. A day of the month after the 28th notes that shorter months are skipped.
- **Problems** show when Create or Save is pressed, by their field, and focus goes to the first; a plan's JSON and a cron are checked as they are typed. Ensemble checks everything again, and its refusal shows above the buttons.
- **A webhook's token, once.** Making a webhook routine, giving it a new token (New token, after a confirm: the old one stops working) or turning a routine into a webhook shows its full address (the API's origin and the routine's path) and its token once, with Copy and a `curl` example: "Copy the token now. You will not see it again." The token is never kept in the browser; afterwards only the address shows.
- **Event routines** name the space they watch when it is not your own ("When a task changes (move) in Acme", Ensemble's `event.spaceName`); the form shows it by name and sends its id back when it is left as it was.
- **Runs.** Run now starts a run whatever the trigger, paused or not, and opens History with it first. History lists the newest 50: Waiting, Starting, Skipped or Failed (with why), then the mission's status (Running, Reporting, Succeeded, Partly done, Failed, Stopped), the trigger (On schedule, On a change, Webhook, By hand), when, and what it gathered ("3 changes"). A run's card is not in the chat (its message's `planId` is the routine's id), so **Open** reads it with its step runs (`GET /api/node/plans/:missionId`) and shows the plan or work card in a drawer, live, with its Stop while it runs, and a link to the conversation it reports in.
- Routines are read again at once when one changes or starts a run (`node.routine` on the event stream) or a run's card changes; a slow poll (5 minutes) only catches up.

## Live behaviour

One EventSource per tab (`/api/node/events`, with credentials). `node.message` / `node.message.updated` merge into every loaded list by id or clientId (and into a plan read with its run cards) and update the sidebar preview immediately. Reactions and old edits do not move a conversation or increment unread counts. `node.status` drives the status halo and typing preview. `node.frame` (owner only) streams text, tool names and known records (`refs`); `lib/live.ts` buffers text once per animation frame for that room, while sidebar busy state changes only at start/stop. In a room with other people, your node's reply being written shows in the tab of the newest person's message (the stream does not say which). `node.room` refreshes the list and pins; `node.invite` refreshes invites; `node.needs` re-reads pending cards immediately (60-second poll fallback); `node.routine` re-reads routines and the changed routine's runs; `node.request` re-reads that room's requests. A run card of a session that changes also re-reads the Sessions list (once per burst), which is otherwise read every 20 seconds while shown; an open session is read every few seconds only while something goes on in it.

The timeline follows new messages and resized/streaming content only while already at the bottom. Reading earlier work keeps its position and offers a counted jump-to-latest. Older-page loads preserve the anchor. Pending sends and their confirmed copies share the same clientId render key, avoiding duplicate bubbles or repeated entrance animations. Only new arrivals get a short entrance, disabled with reduced motion.

Unsent text and whether it is private survive switching conversations in tab memory, scoped by account, room and tab; they are not written to browser storage. (What each tab of a room has shown is: numbers only, no content.) Attachments and reply targets are not part of these text drafts. Read updates are debounced per room, so switching chats cannot cancel the previous room's update. Bootstrap refreshes preserve newer live previews and read markers; failed read writes restore the prior marker and report an error.

Run cards read the job when visible and every 2.5 seconds while active and visible/open; trace steps load only while the work log is open. Ended runs are read once. A changed run message refreshes both immediately. The session of a live run is read (`GET /api/node/sessions/:id`) while its card is on screen, every 2.5 seconds, and again when its card changes. Evidence pictures are read once per page and shared by thumbnails and the lightbox. Reconnects refresh open messages and Needs me, retaining earlier pages.

## Links

Links that leave Node (Ensemble, ensemblework.com, vendors, links in messages) open in a new tab; a link to a room opens here. Sign-in with a provider stays in the same tab, because it returns to Node.

## Responsive and installable

Phones open Chats as a left sheet; selecting a conversation closes it and opens that group's timeline, not a separate form. A conversation uses one header with back-to-chats; other pages retain the global menu/Search/Activity bar. From 768 px the collapsible sidebar is fixed; from 1024 px Activity can be opened on the right. Drawers trap keyboard focus, close on Escape/backdrop and restore the opener. The web manifest makes it installable to a Home Screen (start URL `/chat`). `public/sw.js` is ready for web push (v1).

The conversation scrolls independently of its header and composer. On phones the shell and drawers follow the visual viewport when the keyboard opens; the composer includes the bottom safe area. Form fields use at least 16 px text to avoid Safari's focus zoom. Long names, model/computer metadata, answers and message text wrap within their cards, while fenced code and tool output retain their own horizontal scrolling. The model menu stays inside the phone viewport. Drawers scroll their own content and keep Close in a sticky header.

`InfoTip` makes longer model/permission explanations available on hover, focus or tap, without permanent paragraphs. Errors, privacy labels and approval controls stay visible.

## Browser regression

`e2e/chat-ui.mjs` runs a stateful local API/SSE fixture, never a hosted account or model. Start `pnpm dev` on an unused port, then run it with `NODE_WEB`, `CHROME_PATH` and, when Playwright is supplied externally, `PLAYWRIGHT_MODULE` (the absolute module entry). `NODE_CHAT_SHOTS` optionally saves evidence outside the repository. It exercises five widths, dark/light themes, Markdown tables (headers, linked cells, alignment, escaped pipes and keyboard scrolling), cross-kind recency, rail persistence, group opening, streaming/scroll anchoring, optimistic sends and private text-draft restoration.

`e2e/runtime-cards.mjs` runs the same way and covers the runtime cards at phone and desktop widths: a plan card with held steps, attempts (what they built and tested), checks and the ledger (and the §4.11 brief shown once, on one line), a contract 1 card and a work card; a plan built in worktrees (its facts, an integration step and its links, a stale pass, a step waiting for its place); the session card's settings, queue moves (one refused), cancel, Steer and Stop, the packet it was told, who manages it and Hand to…; an ended session no node manages given to one; a node's card asking to hand a session over; a run asked for its result; evidence (SVG and HTML only as downloads, the lightbox's keys and focus); a node's media; the room's Stop and the "Working on" strip, with a routine's run opening its card; and a helper thread in place of its room in the list, what the helper may do, and keeping it as a node.

`e2e/routines.mjs` covers Routines at 390 and 1280 px: the list by node, an event routine's space by name, pausing and resuming, a scheduled routine made from presets in a searched time zone (its problems first), a webhook routine's token shown once and a new token, Run now, `node.routine` reading the list again, a run's card in a drawer (read with its runs) with what its agent was told, editing, deleting, a node's routines in its settings, and a card's link to its routine.

`e2e/sessions.mjs` covers the Sessions page at 390 and 1280 px: the list newest first (where each runs, its newest task, what it did, who manages it), search, a session no node manages opened (no controls) and given to a node, a managed session opened with its queue, controls, recent runs and Steer, the list read again when a session's card changes on the event stream, and a session's newest card and a run's card opened in their conversation (a Hub session has none).

`e2e/needs-me.mjs` covers the Needs me page at 390 and 1280 px: a proposed node and crew, a request to hand a session over, a question about sharing, a peer request and a card to start work, each in its own words with its link (My crew for a room's cards), answered in place with the count following.

`e2e/rooms-v2.mjs` covers a room with other people at 390 and 1280 px: both tabs and their unread, media in a message read through it, a request card and status cards, `@leads status`, Ask my nodes replying to a Room message and its answer in My crew, the owner's request card (edited, always, accepted), a disclosure card (Allow), a node's proposal (Make it), a helper's thread under the message that asked and its plan step, Share to room through the lead, a new request (a review needs its candidate) and Cancel, the trust sheet (everyone, one person, the budget, a shareable page), away with a note and presence, and Decide in My crew.
