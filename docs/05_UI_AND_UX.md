# 05 · UI and UX

Chat-first teammates with familiar messenger navigation. Ensemble's flavour is Satin Gold on a near-black petrol night, the Woven Chorus mark, Figtree, and Ensemble's own cards (tasks, runs, approvals).

## Principles

- **Chat first.** Every screen leads back to a conversation. The composer is the biggest control on the page.
- **Recognisable signatures.** Nodes keep their own signature faces, with saved shapes, colours and eyes, independently of the model they use. They blink and breathe while thinking; reduced motion keeps them still. Model pickers and agent runs use the actual vendor or agent's mark.
- **Every question waits in the chat.** What a node or a run needs from you is an owner-only card in the conversation where it is talking; the node waits for your answer and goes on by itself. Answered, a card folds into a checkpoint. The chat list marks the chats where something waits, and the Activity panel lists it all.
- **Privacy you can see.** Anything only you can see is marked with a lock and the private (violet) tint: a room's My crew and what is in it, drafts, approval cards, error notices, run cards in shared rooms.
- **Honest status.** "Thinking…", the reply being written, tool chips and run states come from the server, never from timers.

## Model and agent marks

`components/model-logo.tsx` and `lib/model-brand.ts` resolve the actual model first, then a known provider/agent when no model identifies the maker. GPT/Codex, Claude, Gemini, Grok, GitHub Copilot, Cursor and the other supported vendors use local canonical SVGs, shared with the Hub. Model pickers and run cards use these marks; source group icons do not stand in for a model. Node identities in chat headers, messages, sidebars, search results, mentions, settings and node selectors always use `NodeAvatar`, not the model mark.

`public/providers/manifest.json` and `NOTICE.txt` retain provenance and identification-only trademark notices. The Grok SVG is from LobeHub/lobe-icons under its included MIT licence. A public node exposes no private model choice: its signature face uses only its public avatar, never an inferred model.

## Connector logos

`ConnectorLogo` and `lib/connector-logos.ts` are the shared brand renderer and resolver. Connections use the catalog API's `logo` key (falling back to its ID for older responses), not the display name. Native connector tools and catalog MCP tool names use the same assets in completed replies, live tool chips and approval cards. Generic Ensemble tools stay generic; `apps_search` does not identify a service, so it keeps its wrench. Custom MCP names, including ones named after a vendor, are never treated as proof of that vendor's identity.

Assets are local under `public/connectors/`, reused from Ensemble's brand library with per-image provenance in `manifest.json` and licences/trademark attribution in `NOTICE.txt`. Wispr Flow and Zotero use real vendor marks rather than the Hub library's older placeholder lettermarks. This does not add integrations: the API catalog still controls what can be connected.

Tiles have fixed dimensions and contained, unmodified aspect ratios. A neutral white backing keeps black and coloured marks readable in both themes; small chat marks use 16 px tiles and connection rows use 36 px. Adjacent connection names make row logos decorative; standalone/tool logos have accessible names. Unknown logos use initials, custom MCP and CSV use explicit generic icons, and failed image loads retain the same tile with an accessible "logo unavailable" fallback. Branding does not replace connection status text, approval controls or tool-failure indicators.

## The model picker

One picker everywhere a model is chosen: new nodes, new nodes in a crew, and the node's settings. Groups: **Included with Ensemble** (Everyday and Step-up, with relative credits), **Your API keys** (per provider), **Your AI plans on ‹computer›**. The bootstrap carries the included models, so the picker opens at once; own keys and AI plans come from `/api/node/models` when it opens. A filter box appears for long lists, and the server's problems show at the bottom.

## Attachments

Both composers (a conversation's and the start page's) take files (`components/chat/attachments.tsx`, rules in `lib/attachments.ts`):

- **Adding:** the paperclip opens **Upload from this computer** and **Choose from Files**. Files can also be dropped on the composer (it shows "Drop to attach" while files are held over it; a file dropped elsewhere on the page is ignored, so the draft is never lost) or pasted. A picture that comes with copied rich text (the clipboard also has HTML with text in it, or RTF, as Word, Excel and web pages add) is ignored; a pasted screenshot is named "Pasted image ‹date› ‹time›".
- **Upload:** a file from the computer goes to the person's Ensemble Files at once (`POST /api/documents`, `summarize: false`) with real progress, before the message is sent. Any type Files keeps can be attached: text, Markdown, code, data, pictures, PDFs, office files, archives, sound and video. Three are refused before anything is read, in Ensemble's own words and without **Retry** (`attachProblem` in `lib/attachments.ts`): a program or raw binary data (`.exe`, `.dmg`, `.apk`, `.jar`…, the same list as Ensemble's Files), an empty file, and one larger than the server keeps (`usage.maxFileBytes` from `GET /api/documents`: 25 MB on the hosted plan), which says "For a larger file on your computer, tell your node where it is.". Any other refusal (quota) shows the server's own words.
- **Choose from Files:** the person's Files, newest first, searchable by name (`GET /api/documents?q=`). Each row shows kind, size and the date and time it was added, so files with the same name can be told apart. Picking one attaches it without uploading again; picking it again takes it off.
- **The shelf** above the text box has a chip per file: a thumbnail for pictures from the computer (a local preview), name, size, and while uploading the percentage, a progress bar and **Cancel**. Ready files have **Remove** (the file stays in Files). A failed upload shows why, with **Retry** and **Remove**. Up to 8 files per message; the same file is not added twice; a note says what was left out.
- **Sending** waits while a file uploads or after one failed, and says so next to the paperclip. A message may be files only. The paperclip's hint says who can read them: in a DM or crew, the nodes read the text of documents and code and see pictures when their model reads images, and save a file on your computer when asked (it is already in your Files); in a room with other people, nodes read files only from their own owner's messages, and others see a file's name but cannot open it.

## Messages and cards

- **Your messages** sit on the right in a gold-tinted bubble; private ones are violet (outside My crew, with a lock and "only you and your nodes").
- **Node messages** sit on the left with the node's signature face and name; someone else's node retains its owner label. Repeated handles are omitted from message headers. Markdown subset: headings, lists, code, quotes, bold, links (bare and `[label](address)`) and GFM tables; known `@handles` are highlighted. Tables have column headers, aligned cells and the same inline formatting and safe links as other message text. Escaped pipes stay in cells; wide tables scroll sideways in a keyboard-focusable region without widening the conversation. Raw HTML stays text.
- **Records by title.** A node names Ensemble records by title, never by id (`lib/entity-text.ts`, the same rules as Ensemble's [docs/11 §4.1](https://github.com/ensemblework/ensemble/blob/main/docs/11_HOW_THE_ASSISTANT_WORKS.md#41-records-by-title-ids-for-machines)). A record link (`[@Draft brief](ensemble://task/…)`) shows its label and opens the record in Ensemble; a room opens here. A bare id of a record the message names (its `data.refs` and its tool chips' `refs`) shows as that record's title, linked; records with the same title get their kind, due date or a number. An id or record link in brackets right after the record's own title ("Expire Needs Me requests when their task ends (ensemble://task/…)") turns those words into the link, whether they are the whole title or its first clause; the title is never shown twice. In a node's messages and on cards (briefs, reports), a record link nobody named shows as its kind, linked ("(task)"), never as an `ensemble://` address; a person's `[label](ensemble://task/…)` opens the record too, and a custom board's (`ensemble://board/…`) opens that board. Unknown ids, code, quotes and other links stay as written, ids stay when someone in the turn asked for them (`data.showIds`), and what people write is never changed. Conversation previews, pins, reply quotes and Copy read the same way (`readableBody`). Text being written holds back a half-written id, using the turn's `refs` frame and its tool calls.
- **Code blocks** show the fence's language and a copy button above the code, which scrolls sideways instead of wrapping, also on a phone (`components/chat/code-block.tsx`).
- **Message actions** appear on hover or focus, or after a long press on a phone: react (the eight reactions), reply, copy, pin or unpin (only messages everyone in the room can read), delete (your own). Reactions show under the message with counts; yours are highlighted and the tooltip names who reacted.
- **Replies** quote the original above the message; the quote goes to it. A reply to a private message is private too. In a room's Room, replying with **Ask my nodes** asks your nodes about that message privately, quoting it.
- **Deleted messages** read "Message deleted".
- **Files on a message** (`components/chat/file-chips.tsx`) sit under its words as chips with kind, name and size. Your own link to the file in Ensemble's Files (`/files/:id`, new tab), and your pictures show a thumbnail read with your session (`GET /api/documents/:id/original`) once the chip is near the screen. Someone else's show only the name, kind and size with a lock; the tooltip says only that person can open it and your nodes see its name only. In a DM or a crew, each of your own files has **Save on my computer** beside it: it puts "Save “brief.pdf” on my computer." in the composer as a reply to that message, so the node knows which file (it saves it with its own tools, Ensemble docs/35). A message with only files previews as "📎 name" or "📎 3 files" in lists, pins and quotes.
- **Media in a message** (`data.media`: `evidenceId`, `kind`, `mime`, `name`, `size`, `caption`; a node's reply, a file it shared from your computer or a folder it zipped there, a plan's report, an approved draft, a shared message): pictures in a grid, videos and sound in a player, Markdown, code and other text as previews, other files as downloads with their type, in the same gallery as [evidence](#evidence), on a phone as on a computer. Each piece is read through its message (`GET /api/node/evidence/:id?message=`), which is how others in a room may open it, its poster too. What capture measured (`width`, `height`) keeps its space while it loads. A message with only media previews as "📎 2 pictures, 1 video", or by its name when it is one file ("📎 site.zip").
- **A task assigned to a node** (`data.task` on its message: `id`, `title`, `due`): the node's reply when it is given a task (Ensemble docs/35) has a chip under its words, "Task · Fix the login redirect · due 3 Nov", that opens the task in Ensemble. It shows no status: the message keeps the task as it was then.
- **Shared to the room:** a copy shared from someone's My crew says so over its words ("Shared from Mira's crew", "Shared by Mira" when their lead posted it, "· @scout's reply" when it was another node's words); on your own, the line goes back to where it came from. The private original says "Shared to room", which goes to the copy.
- **Not sent:** a message the server refused stays with its reason, **Retry** (the same words, files and clientId, so nothing is uploaded again and the server keeps one copy) and **Edit** (back into the composer with its files, and its reply when that message is loaded).
- **Tools a reply used** fold into one line under it, "Used 4 tools · Search tasks, Read page, Assign to agent +1 · 1 failed", which opens into the tool chips: what the node did in Ensemble ("Create tasks · Added “Draft brief”."), each linking to the item in the Hub. A reply that used one tool shows that chip alone. They are shown only where nobody else reads.
- **Approval card** (owner-only; its words are in `lib/cards.ts`): "@node wants to do this for you" with each held call as Ensemble describes it, by record titles, keeping its line breaks (pick some with checkboxes when there are several) → Approve / Discard; "@node wants to start work on your computer" with the agent, place and message → Start it / Discard; "@node wants to hand a session to @designer" with which session and its note (`action: "hand_over"`: no prompt or title) → Hand it over / Discard, then "Handed over" and "@designer manages this session now."; or "Post this in “Launch” for you?" with an editable draft → Post / Discard ("Post this answer…" when it answers someone; a request your lead drafted is "Send this request to @ben?", [below](#rooms-with-other-people)). States: Waiting for you, Applying…, Approved, Partly applied, Posted, Discarded; errors keep the card pending.
- **Waiting for you, then a checkpoint** (`components/chat/owner-card.tsx`, words in `lib/checkpoints.ts`): every owner-only card (the approval card above and those below) stays open while it waits for you, with a gold edge and a pulsing "Waiting for you", and while its answer is carried out (applying, saving, signing in, running). Once settled it folds into a checkpoint in the chat: a small round mark and one line, such as "Allowed @assistant-3 to browse walmart.com · Once", "Ran as administrator: apt-get install -y xvfb · exit 0", "Didn't allow @x to run commands in live-test", "Saved secret STRIPE_KEY", "Signed in to github.com", "Passed the human check on walmart.com", "Allowed GitHub Copilot to run python3 search.py · Once", "Answered: “Use main”" or "Added @tester to the crew". A checkpoint sits under the node's previous message; a click (or Enter) opens the card read only and closes it again. An answer given here shows at once, before Ensemble updates the card.
- **Question from your computer** (owner-only, `data.type: "computer"`, `components/chat/computer-card.tsx`): your computer asks before a node uses one of its folders for the first time, or opens a new website when you turn that on (Settings → Browsing). "@assistant-3 wants to run commands in live-test on Akash's-HomeServer", what it tried in monospace ("Run: npm test"), the folder or website and the computer, then the computer's own answers, the lasting one first, since you are asked at most once per folder: **Allow in this folder from now on** (**Allow this address from now on** for a website; the computer's "Always for this folder"), **Only this mission**, **Just once** and **Don't allow** (`computerChoices` in `lib/checkpoints.ts`). The node's call waits for the answer and goes on by itself. The answer is Ensemble's decision for the card (`POST /api/decisions/:id/decide`, the computer's own words for the option as `reason`), so answering it in the Hub, the CLI or on a phone settles the card too. States: Waiting for you, Allowed, Not allowed, Expired.
- **A run's question** (owner-only, `data.type: "run_decision"`, `components/chat/run-decision-card.tsx`): a coding agent in a run a node started asks to run a command, or asks which way to go (Ensemble's run decisions, docs/35). Ensemble posts the card where the run's card is, privately when that one is. "GitHub Copilot wants to run a command" (or "GitHub Copilot asks you"; the agent named by the card, else by the run's own card, else "@node's run"), the agent's words ("Run python3 search.py?"), the command in monospace, the folder and "In the run “‹title›”", which goes to the run's card. A permission has **Allow once** and **Don't allow** (and **Allow for this run** only when Ensemble's own record says the run takes it: a paired computer takes answers from the web once only); a question has its options with the recommended one marked, a box for your own words when the agent takes them, and "Skip, let the agent decide". A risky one asks to confirm first, also when Ensemble only says so on answering; one only its computer may approve offers Don't allow here. The answer is Ensemble's decision (`POST /api/decisions/:id/decide`: an option or your words as `reason`), so the first answer counts wherever it is given. The card follows every answer, its expiry and the run's end, and folds into a checkpoint: "Allowed GitHub Copilot to run python3 search.py · Once", "Didn't allow GitHub Copilot to run rm -rf build", "Answered: “Use main”", "Skipped, the agent chose: Which branch?", "@lead allowed GitHub Copilot to run npm test · Once" when its node answered, "No answer in time: …" or "The run ended before an answer: …". Opened, it says who answered and when. States: Waiting for you, Allowed, Answered, Not allowed, Skipped, Expired, Closed.
- **Command as administrator** (owner-only, `data.type: "sudo"`, `components/chat/sudo-card.tsx`, rules in `lib/sudo.ts`): "@node wants to run a command as administrator on ‹computer›" with the exact command, why, the computer and the folder. You type the computer's password on the card: it is encrypted in this browser for that computer's key (`GET /api/node/sudo/:messageId`, the sealed box secrets use, `purpose: "sudo"`), bound to the card and the SHA-256 of the exact command shown, cleared from the page once sealed, and never stored, logged or shown to a node or a model. **Run as administrator** sends the sealed password, **Run without a password** is for a computer where sudo needs none, and **Don't run** ends it (`POST /api/node/sudo/:messageId`). A computer that cannot take a password from here says why ("Update Ensemble on ‹computer›…"), and one that is offline says so. A password the computer refused opens the card again with why and the tries left (three in all). Then Running…, Done (exit 0), Failed with its exit code or why, Not run, or Expired.
- **A node for the crew** (owner-only, `data.type: "crew_add"`): a crew's lead wants one of your existing nodes in the crew. "@lead wants to add @tester to this crew" (the crew by name when the lead asks from its own chat) with the node and why → **Approve** (it joins as a member) / **Not now** (the lead goes on without it).
- **Secret card** (owner-only, also in the Hub's Needs me; `components/secret-box.tsx`, words in `lib/secret.ts`): "@node needs a secret: NAME" with why, a password box ("Paste NAME"), **Only send it to** (optional origins, filled with what the node suggested), a line on how the value travels, Save to ‹computer› and Decline. The line is accurate for each case:
  - The computer has a key: "Encrypted in this browser for ‹computer›: only ‹computer› can read it, and Ensemble's server passes it on without being able to. Key 7F98 5267 E5FD 5A05: it should match `ensemble secrets fingerprint` on ‹computer›." The fingerprint is worked out in the browser from the key it encrypts for.
  - An older computer: "Sent over HTTPS to Ensemble's server, which passes it to ‹computer› without keeping it. ‹computer› is too old for end-to-end encryption; update Ensemble there."
  - Its key changed: "‹computer› now reports a different key from the one it was paired with, so nothing is sent to it. Pair it again (`ensemble login`), then type the value again." The box is disabled.
  - Then what happens to it: with destinations, "Kept encrypted on ‹computer› for use by reference only: runs there send it to ‹origins› without seeing it, and it is never put in a run's environment"; without, "Kept encrypted on ‹computer›; runs there that may have it get it as $NAME".

  The value is sent once and never shown again; the card then reads "Saved on ‹computer›. Runs there get it as $NAME." (or "use it by reference only, sent to ‹origins›"), with "Encrypted end to end." or "Sent over HTTPS through Ensemble's server (not end to end)." Errors (computer offline, no answer, a refused box) keep the box open. Settings → Computers shows each computer's **Secret key** fingerprint, or that it changed, or that secrets go over HTTPS only.
- **Sign-in card** (owner-only, also in the Hub's Needs me; `components/login-box.tsx`, words in `lib/login.ts`, Ensemble docs/35 §8.16.1): a node's tab on the computer waits for you to sign in to a site (`purpose: "sign_in"`), or to pass a human check there ("Verify you are human", "Press and hold"; `purpose: "human_check"`). "@node needs you to sign in to portal.azure.com", or "@node needs you to pass a human check on walmart.com", with the computer and why ("On Mira's laptop · Why: the page has a password field."), and:
  - **Sign in here** (**Open it here** for a human check; when the computer can show its pages here, `takeover`): the remote view below, on this phone or computer. Google sign-in, codes and approvals, and making an account all work there; the computer sees when you are through and carries on by itself. On a computer it adds "Works on your phone too · **Open on your phone**", which shows this card's link (`/r/‹room›#m-‹card›`) as a QR code (`lib/qr.ts`, made in the page; `components/qr-code.tsx`, loaded only when shown) with **Copy link**: scanned, the card opens on the phone (signed in to Node there), and Sign in here works the same.

A table on wider screens, one block per setting on phones.

A queued run says its place in line and can be cancelled.

"Answer it in Ensemble" shows only when the run waits on something not listed here.

### Evidence

Files a run attached (`data.evidence` on its run card: screenshots, videos, traces, reports, logs) show as a gallery (`components/chat/evidence.tsx`, rules in `lib/evidence.ts`) on the run card, and on its plan step, which gathers its runs' evidence. A node's media (`data.media`) uses the same gallery in its message.

- **Pictures** (PNG, JPEG, GIF, WebP, AVIF) show as thumbnails read with your session (`GET /api/node/evidence/:id`; media in a message through it, `?message=<id>`) once they are near the screen, and only when the bytes that come back are such a picture. Several sit in a grid (two side by side; three in a row from 640 px). A tall picture (a full-page capture, at least 2.2 times taller than it is wide, as measured or once it loads) shows its top, cropped, with "Tall image · open to scroll"; opened, it fills the width, never larger than it is, and scrolls from its top. They open in a lightbox: the picture large, its caption, "2 of 5", Download and Close. Arrow keys move, Home and End go to the first and last, Escape closes and focus goes back to the thumbnail; on a phone a swipe moves.
- **Videos** play in a player with its controls in place, showing their poster (a first frame when they have none) and their length until played (and larger in the lightbox). One that cannot be read becomes a download.
- **Sound** (MP3, WAV, Ogg, M4A, AAC, FLAC: by its type, or by its name when the type says nothing, since Ensemble does not type sound by its bytes) plays in a player under its name, type, length and size, with **Download**; one that does not play says so and stays a download.
- **Size.** A single picture or a video keeps the shape capture measured while it loads, no wider than the card and no taller than about 420 pixels; several pictures share one shape so the grid stays even.
- **What a file is** (`lib/file-types.ts`): its name's extension first, since Ensemble types a file by its bytes and many share one type (a `.docx`, `.xlsx` or `.pptx` is a ZIP, a `.py` plain text, a `.ts` JavaScript), else its type. Each has an icon tinted by its family and a label: "Markdown", "Python", "TypeScript", "JSON", "CSV", "Log", "PDF", "ZIP archive", "Word document", "Excel spreadsheet", "PowerPoint", "MP3 audio", "File"…
- **Text files** (Markdown, code, plain text, logs, CSV, TSV, JSON, YAML…; `lib/file-preview.ts`) show as a preview when their type is text (or none): the name, its type, size and lines, **Copy** (not for Markdown), **Download**, and its first 40 lines, kept short on screen with a fade. Markdown is rendered as in a message (raw HTML stays text); code has line numbers, which copying leaves out, and long lines scroll sideways; JSON is indented; other text is in monospace. There is no syntax colouring. **Show all** opens it in a box that scrolls; **Collapse** folds it again. At most the first 200 KB is read, through the message that shows it, once it is near the screen; "The first 200 KB. Download it for the rest." says when there is more. A preview is always text, never a page: a `.md` or `.vue` file Ensemble typed as HTML (because it mentions a script tag) is still previewed by its name, and nothing in it runs.

Nothing active is ever shown in the page. A download says how far it has got ("Downloading 42%") and saves the file under its name.

- **Held and kept files** are listed, never read: "Held for you to check first" (its card in the conversation previews it) and "On the computer, not uploaded" (evidence upload is off there).
- **Why a file cannot be read**, in the server's words when it gives them, else: the computer did not answer in time (504), too large to preview from the computer (413), kept on the computer, not uploaded (409), not available any more (404).

### Helper threads

A helper's room (`kind: "task"`) is not in the conversation list (`lib/threads.ts`). A helper's task is a step of its parent's plan. Under the message that asked for the work, a chip reads "@scout, helper of @lead · working · 4 messages" (or quiet). It opens in place to the helper's conversation, read only: the brief its parent wrote (**Brief**), what it is writing now, and its report (**Report · Done**, Pass, Fail or Blocked), with "Open the helper's room". Its parent tells you once, when all its helpers have reported. Reading it there marks the room read. A link to a helper's room still opens it, read only.

- **Where it shows.** Ensemble's room view says whose helper it is and where (`helper`: the parent, the helper, the origin room, whether it was asked privately, the message that asked, `originMessageId`, and the plan card its step is in, `planId`). The thread goes under that message, whoever wrote it; when it is not loaded, under that plan card; and the plan card's step for the helper has it too. Rooms from before these marks go under the parent's reply whose `node_helper` call names the helper or its room, or, read from their members, to the parent's direct chat. A helper none of these places is under Helpers in the "Working on" strip and opens in a side panel.
- **Asked privately.** A helper asked for in your My crew (`originPrivate`) shows only under a private message or card, and its chip carries the lock and the private tint, here and in the strip.
- **What it may do.** The thread's header says it: "Can read", "Can run sessions" or "Can use the computer" (the helper's `autonomy.grant`), and that it reports to its parent. The helper's room settings say the same.
- **Keep as a node.** In the thread's header and the room's settings, after "Keep @scout as a lasting node? It gets its own chat." (`POST /api/node/nodes/:id/promote`). The helper leaves its parent, keeps its charter and memories, and its own chat appears in the list. The thread then reads "Kept as a node" with "Open its chat"; its room stays as history, and deleting that room leaves the node.

### Working on

Under a conversation's header, a one-line strip lists what is working there, from what is already loaded: your live plans and pieces of work ("2 of 6 done", the work's progress), routines' runs that report here, your agent sessions with a live run, one per session ("Running · 2 queued"), and helpers that are working. A chip opens its card in the timeline; a routine's run, whose card is not in the timeline, opens its card in a side panel. Quiet helpers whose message is not on screen follow under Helpers. The strip scrolls sideways on a phone and is gone when nothing runs.

### Stopping work

While your work runs in a conversation (a live plan or work card, a live agent run, or a reply being written), its header has **Stop**; More always has "Stop this conversation's work". Both, and the composer's stop button while a node writes, call `POST /api/node/rooms/:id/stop`, which stops your nodes' replies, plans and their runs there. They ask first only when plans or runs are going on; stopping a reply being written does not ask. The result shows in a note ("Stopped. What was changed so far stays." or "Nothing was running here."). A plan or work card has its own Stop while it runs (`POST /api/node/plans/:id/stop`, after a confirm), and a session's Stop keeps or drops its queue.

## Rooms with other people

A room with other people follows rooms v2 (Ensemble's [docs/35 §12](https://github.com/ensemblework/ensemble/blob/main/docs/35_ENSEMBLE_NODE.md#12-rooms-with-people)). The website's side is `components/chat/room-view.tsx`, `room-cards.tsx`, `room-people.tsx`, and for the room's work `room-board.tsx`, `room-work.tsx` and `room-space.tsx`, with rules in `lib/rooms.ts`, `lib/room-work.ts`, `lib/trust.ts` and `lib/cards.ts`.

| Tab | Who reads it | What is in it |
| --- | --- | --- |
| **Room** | Everyone in the room | What people send to everyone, leads' answers, shared copies, request cards, status cards, system lines |
| **My crew** | You and your own nodes | What you ask your nodes and their answers, your plan and run cards, your cards to decide (requests for you, questions about sharing, drafts, proposals), your lead's notes of what changed for you and your catch-up |
| **Board** | People in the room's space (everyone sees which space it is) | The space's tasks, the pages the room follows and its decisions ([The room's work](#the-rooms-work)) |

- **Unread per tab.** Ensemble keeps a read marker and an unread count for each tab (`readSeq` and `unreadRoom` for the Room, `readSeqCrew` and `unreadCrew` for My crew); the tab you read moves only its own (`POST /api/node/rooms/:id/read {tab, upTo}`). Each tab shows its count, opens at its first unread, and a message arriving in the other tab counts there at once. A message link, a search result or a card's button opens the tab it is in.
- **Who answers.** A message that names no node wakes nobody. Only a lead answers in the Room, and only when someone names it; naming someone's other node goes to their lead; your own other nodes answer you in My crew. Nodes' messages wake nobody. The empty tabs, the composer's choice and each node in the @ list say this briefly ("your lead: answers in the Room", "Ben's node: their lead answers").
- **The composer.** In the Room: **Send to everyone** (the default) or **Ask my nodes**, which sends privately to your lead (or the node you name) and opens My crew, where its answer comes; replying to a Room message this way quotes it. In My crew everything is private ("Only you and your nodes"). Each tab keeps its own unsent text. The handshake button asks someone something (below).
- **`@leads status`** as the whole message (punctuation allowed) is said as you type it: "Ensemble answers with everyone's status card. No node is woken." The answer is a **status card** per person, built by code: presence (online, away, offline), away until when and their note, and their missions and tasks for this room at the detail they chose (titles, or with requirements and steps), or that they ask first or share nothing.
- **Share to room.** On your private messages and your own nodes' private replies in My crew, the message actions offer Share to room: **As me** or **Through @lead** (`POST /api/node/messages/:id/share`). The copy goes to the Room; the original says "Shared to room".
- **Requests** ("Ask someone here…": the composer's handshake, More, or the room's settings): to one person, a Question, Share, Review or Work, with what you need; a review names its exact candidate (a commit with its repository, or a web address), and work may. Their lead answers questions and shares within their rules; reviews and work wait for their yes. The public **request card** shows only what the requester wrote, who asked whom, the kind and its state (Open, Waiting for Ben, Accepted by Ben, Answered, Declined, Done, Cancelled), with **See the answer** (a link to the answer in the room, never a copy) and **Cancel request** for the person who asked while it is undecided. A decline note is for the two people alone: on their view of the card ("Ben's note, for you alone: …", from the room's list of requests) and, for the requester, as a private line in My crew with **The request**. The person asked has **Decide in My crew**, which opens their own card: who asks for what, the candidate, which of their nodes would do it and what it costs, with **Accept**, **In my words** (accept with your own words for your lead: the card keeps what was asked and shows your words beside it, privately, and the room never reads them), **Decline** with a note only the requester reads, and "Always accept reviews from Ben in this room". Accepted, a proposed task's card also says how it runs. The cards change in place (`node.message.updated`); the list is read again on `node.request`.
- **Requests your lead drafts.** Asked in My crew to ask someone something, your lead drafts the request instead of sending it: "Send this request to @ben?" with its kind and who it is for, its words as the room would read them (yours to edit) and its candidate, which goes with it only while its values stay in the words ("goes with it", or "stays out") → **Send request** / **Discard** (`POST /api/node/approvals/:id {decision, body}`). Sent, it reads Sent, with **See it in the room**; the Activity panel lists it as "drafted a request to @ben for you to send".
- **Questions about sharing** (disclosure cards, owner-only): "May @lead share this with the room?" with who asked what and what it would share → **Allow** / **Don't share**. Allowed, the lead writes the answer as the usual "Post this answer… for you?" draft; "See it in the room" once posted. Not shared, the room gets only "Mira chose not to share that.". A question to answer in the lead's own words (it uses your credits) reads **Answer** / **Don't answer**.
- **Away.** In the room's settings, "Set away": until you are back, for an hour, until 18:00, until tomorrow at 09:00 or until a time you pick, with a note (`PUT /api/node/rooms/:id/status`); **I am back** ends it. Everyone's presence shows as a dot beside their name in the room's settings, with their away line, read again when someone's presence or card changes (`node.presence`, `node.cards`).
- **Since you joined.** You see, react to, reply to, pin and log only messages from since you joined. A reaction or pin refused for an older message says so in a short note ("You can react only to messages from since you joined.").
- **How many people.** A room holds as many people, counting open requests, as its creator's own limit allows (`limits.roomPeople` in the bootstrap, 10 unless changed in Ensemble's Settings › Sharing, at most 50). The new-room form and the room's settings say so; a full room links to that setting.

**What your lead may share** (More, or the room's settings) is a sheet of your own rules for this room (`GET/PUT /api/node/rooms/:id/trust`): for everyone here, and for one person over that (Change, and a reset to everyone's). Only what changed is sent, on Save.

| Setting | Choices (default first) |
| --- | --- |
| Status questions | Answer from my status card · Ask me first |
| How much of my status | Titles · Nothing · Details |
| Items in the room's shared space | Share them · Ask me first |
| Anything else of mine | Ask me first · Never |
| Answers in its own words | Allow · Ask me first |
| Requests for work and reviews | Ask me · Accept on its own (with which: reviews, work) |
| Monthly budget | Credits a month for answers in its own words; empty for no limit, with what was used this month |

Under it, **Items it may share here**: pages, tasks and files your lead may read out in this room without asking (`GET/PUT /api/node/rooms/:id/shareable`), found by name in your own space and the room's space (`…/shareable/candidates`, each named by its space when there are two), and taken back with ✕.

### The room's work

A room's work lives in a space (Ensemble's [docs/35 §12.11–12.14](https://github.com/ensemblework/ensemble/blob/main/docs/35_ENSEMBLE_NODE.md#1211-the-rooms-shared-space)). Everyone sees which space it is; only people in it see its board.

- **The room's space.** Its creator links a space they own or makes one for the room ("Launch space") in the room's settings, or unlinks it (after a confirm: the space, its board and its members stay as they are). Linking offers everyone else membership as an editor on a private card in My crew: "Join “Launch space”?" → **Join as editor** / **Not now** (which can still become Join, there or on the Board). Joining the room does not add anyone to its space. The header names the space; the Board opens it in Ensemble (`?openSpace=`).
- **Board** (the third tab; `GET /api/node/rooms/:id/board`): proposed tasks first, in a dashed amber row, then In progress, Waiting, To do and Done (folded). Each task says who it is with, who asked for it and through which node, by the handle the board gives ("with you · asked by Ben through @atlas"), and stands out when it is High or Critical, due today or overdue. A proposed task from a request is decided on its card: **Decide in My crew**. A task of mine that came from no request (a steward's proposal, a task now mine) has **Start**; a steward's proposal also **Decline**, with a note only whoever asked reads (`POST /api/node/rooms/:id/tasks/:taskId/decline {note?}`): they get a private line in their My crew with **The board**. My own plan for a task shows on its row ("Your plan" with its state, only for me), opening its card in My crew; while it runs, the row has no second Start.
- **Starting work** asks one question, the same on a request's card, on the Board and on the lead's note:

  | Choice | What happens |
  | --- | --- |
  | Private work, shared result (the usual) | It runs in your own space. The room gets the result and its evidence on the task, never the run or its code |
  | Shared run | It runs in the room's space, where its members see the run as it goes |

  `POST /api/node/requests/:id/accept {mode}` for a request; `POST /api/node/rooms/:id/tasks/:taskId/start {mode}` for a task (`{started, taskId, turnId}`). Then "Started: your lead plans it in My crew."; its plan then shows on the task's row. While your lead here is paused, the question stays open with why ("Your lead here is paused: resume it first.").
- **Your lead's notes** (`data.type: "room_events"`, private): what changed for you in the room's space, at most once a minute, in your lead's words ("Ben assigned you “Landing copy”. Shall I start it with @builder?"), with what it is about (each task or page opens in Ensemble; a mention in the room goes to the message), **Start** for tasks now yours (and **Decline** for one proposed to you from the steward's notes), and a contract's changed lines (`+` added, `−` removed) with the tasks of yours it touches: nothing changes until you say so.
- **Catch-up** (`data.type: "digest"`, private): when you come back from away, or after a long gap, your lead's few lines "While you were away" (or "Since you were last here"), with **Everything it gathered**: what was asked of you, what is proposed to you, changes for you, the board, results, decisions and who wrote in the room; each goes to its card, message or the Board.
- **Results.** Work that delivers to the room comes back to you first as a draft: "Post this result in “Launch” for you?" with its words (yours to edit), its media and the task it went onto ("1 file is on the task") → **Post** / **Discard**. Posted, the Room shows it as a **Result** with how it ended (Done, Partly done, Failed; a review's Pass or Fail), its media and its task.
- **Pages the room follows** (on the Board): watched pages, contracts and the decisions log, each with how many watch it and **Watch** / **Watching**; people who can edit the space set what each page is to the room. **Follow a page** finds one of the room's space by title and watches it, or makes it the contract or the decisions log. The room's line for a change of role links the page; one that lost its role says which ("Contract → Watched").
- **Decisions** (on the Board): a room message enters the log when someone who can edit the space confirms it, with ✅ on it or a reply "log this". Each says who said it and who logged it, and whether it replaces an earlier one or was replaced; "In the room" goes to the message, and the log opens in Ensemble. The room's line "Mira logged a decision: …" has **All decisions**.
- **When your work here is done** (the room's settings, with a space): a result delivered for your task moves it to Done, or **I close my tasks**.
- **Steward** (the room's settings): make one of your nodes in the room (not your lead) the steward; it writes meeting notes, with a proposed task for each person named, and suggests how to tidy the board, only when someone names it, for whoever asks. Its usage and drafts are yours; you or the room's creator end it.

## Routines

A routine is work a node does on its own: on a schedule, when tasks or pages change in Ensemble, or when a webhook calls (Ensemble's [docs/35 §6.5](https://github.com/ensemblework/ensemble/blob/main/docs/35_ENSEMBLE_NODE.md#65-routines)). `/routines` lists them all by node (`components/routines.tsx`, rules in `lib/routines.ts`), from the sidebar and Settings; a node's settings list its own, with New routine for that node.

**The form** opens in a drawer (in a node's settings, in place) and fits a 390 px phone:

| Field | What it takes |
| --- | --- |
| Title | Up to 120 characters |
| Node | One of your nodes, never a helper. A routine's node does not change once it is made |
| Reports in | The node's chat (the default) or one of your crews it is in: only where you read alone |
| What it does | **Instruction** (the default): work the node does itself. **Saved plan (advanced)**: a plan as a lead makes one (`node_plan`: goal, requirements, constraints, steps), as JSON, run as a plan in the node's crew |
| When | **Schedule**: every day at, weekdays at, every week on ‹day› at, every month on ‹day› at, every hour at :mm, or a custom cron, in a time zone (the browser's by default; search by city or region). **Event**: a task or a page changing, only for the actions ticked (task: created, updated, moved, assigned, deleted, agent run; page: created, saved, deleted; none ticked: any change), in your own space or one you name, gathered for 60 seconds by default. **Webhook**: its own address and token |
| Tell me | Always post the result · Only when something needs me · Never post (keep a log) |

- **Schedules.** A preset becomes a five-field cron in the browser and reads back before saving ("Every Friday at 16:30 (Europe/London) · 30 16 * * 5"); once saved, the list shows Ensemble's own words for it. A cron that is one of the presets opens as that preset. A day of the month after the 28th notes that shorter months are skipped.
- **Problems** show when Create or Save is pressed, by their field, and focus goes to the first; a plan's JSON and a cron are checked as they are typed. Ensemble checks everything again, and its refusal shows above the buttons.
- **A webhook's token, once.** Making a webhook routine, giving it a new token (New token, after a confirm: the old one stops working) or turning a routine into a webhook shows its full address (the API's origin and the routine's path) and its token once, with Copy and a `curl` example: "Copy the token now. You will not see it again." The token is never kept in the browser; afterwards only the address shows.
- **Event routines** name the space they watch when it is not your own ("When a task changes (move) in Acme", Ensemble's `event.spaceName`); the form shows it by name and sends its id back when it is left as it was.
- **Runs.** Run now starts a run whatever the trigger, paused or not, and opens History with it first. History lists the newest 50: Waiting, Starting, Skipped or Failed (with why), then the mission's status (Running, Reporting, Succeeded, Partly done, Failed, Stopped), the trigger (On schedule, On a change, Webhook, By hand), when, and what it gathered ("3 changes"). A run's card is not in the chat (its message's `planId` is the routine's id), so **Open** reads it with its step runs (`GET /api/node/plans/:missionId`) and shows the plan or work card in a drawer, live, with its Stop while it runs, and a link to the conversation it reports in.
- Routines are read again at once when one changes or starts a run (`node.routine` on the event stream) or a run's card changes; a slow poll (5 minutes) only catches up.

## Live behaviour

One EventSource per tab (`/api/node/events`, with credentials). `node.message` / `node.message.updated` merge into every loaded list by id or clientId (and into a plan read with its run cards) and update the sidebar preview immediately. Reactions and old edits do not move a conversation or increment unread counts. `node.status` drives the status halo and typing preview, and `waiting` (with its card) shows the node waiting for your answer, with **Go to the card**. `node.frame` (owner only) streams text, tool names and known records (`refs`); `lib/live.ts` buffers text once per animation frame for that room, while sidebar busy state changes only at start/stop. In a room with other people, a reply being written shows in the tab it is for: `node.status` and `node.frame` say whether it is private (My crew) or for the Room. `node.room` refreshes the list and pins, and in a room with other people its space, board, pages, decisions and steward; `node.presence` and `node.cards` re-read its status cards; `node.invite` refreshes invites; `node.needs` re-reads agents' questions and run approvals immediately (60-second poll fallback); `node.routine` re-reads routines and the changed routine's runs; `node.request` re-reads that room's requests; `node.live` (owner only) reads that run's live picture again, or shows at once why it paused. A run card of a session that changes also re-reads the Sessions list (once per burst), which is otherwise read every 20 seconds while shown; an open session is read every few seconds only while something goes on in it.

The timeline follows new messages and resized/streaming content only while already at the bottom. Reading earlier work keeps its position and offers a counted jump-to-latest. Older-page loads preserve the anchor. Pending sends and their confirmed copies share the same clientId render key, avoiding duplicate bubbles or repeated entrance animations. Only new arrivals get a short entrance, disabled with reduced motion.

Unsent text and whether it is private survive switching conversations in tab memory, scoped by account, room and tab; they are not written to browser storage. Attachments and reply targets are not part of these text drafts. Read updates are debounced per room, so switching chats cannot cancel the previous room's update. Bootstrap refreshes preserve newer live previews and read markers; failed read writes restore the prior marker and report an error.

Run cards read the job when visible and every 2.5 seconds while active and visible/open; trace steps load only while the work log is open. Ended runs are read once. A changed run message refreshes both immediately. The session of a live run is read (`GET /api/node/sessions/:id`) while its card is on screen, every 2.5 seconds, and again when its card changes. Evidence pictures (and video posters) are read once per page and shared by thumbnails and the lightbox; a held capture is read only when you preview it. A working run's live view is read while its card is on screen: when `node.live` says it changed, else every 3 seconds once the computer sends pictures (every 15 seconds before, every 12 while the stream keeps up). Reconnects refresh open messages and what waits for you, retaining earlier pages.

## Links

Links that leave Node (Ensemble, ensemblework.com, vendors, links in messages) open in a new tab; a link to a room opens here. Sign-in with a provider stays in the same tab, because it returns to Node.

## Responsive and installable

Phones open Chats as a left sheet; selecting a conversation closes it and opens that group's timeline, not a separate form. A conversation uses one header with back-to-chats; other pages retain the global menu/Search/Activity bar. From 768 px the collapsible sidebar is fixed; from 1024 px Activity can be opened on the right. Drawers trap keyboard focus, close on Escape/backdrop and restore the opener. The web manifest makes it installable to a Home Screen (start URL `/chat`). `public/sw.js` is ready for web push (v1).

The conversation scrolls independently of its header and composer. On phones the shell and drawers follow the visual viewport when the keyboard opens; the composer includes the bottom safe area. Form fields use at least 16 px text to avoid Safari's focus zoom. Long names, model/computer metadata, answers and message text wrap within their cards, while fenced code and tool output retain their own horizontal scrolling. The model menu stays inside the phone viewport. Drawers scroll their own content and keep Close in a sticky header.

`InfoTip` makes longer model/permission explanations available on hover, focus or tap, without permanent paragraphs. Errors, privacy labels and approval controls stay visible.
