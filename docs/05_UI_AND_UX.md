# 05 · UI and UX

Chat-first teammates with familiar messenger navigation. Ensemble's flavour is Satin Gold on a near-black petrol night, the Woven Chorus mark, Figtree, and Ensemble's own cards (tasks, runs, approvals).

## Principles

- **Chat first.** Every screen leads back to a conversation. The composer is the biggest control on the page.
- **Recognisable signatures.** Nodes keep their own signature faces, with saved shapes, colours and eyes, independently of the model they use. They blink and breathe while thinking; reduced motion keeps them still. Model pickers and agent runs use the actual vendor or agent's mark.
- **What needs you is never buried.** Approvals are owner-only cards in the conversation, mirrored in the Activity panel with a badge.
- **Privacy you can see.** Anything only you can see is marked with a lock and the private (violet) tint: Only‑me messages, drafts, approval cards, error notices, run cards in shared rooms.
- **Honest status.** "Thinking…", the reply being written, tool chips and run states come from the server, never from timers.

## Model and agent marks

`components/model-logo.tsx` and `lib/model-brand.ts` resolve the actual model first, then a known provider/agent when no model identifies the maker. GPT/Codex, Claude, Gemini, Grok, GitHub Copilot, Cursor and the other supported vendors use local canonical SVGs, shared with the Hub. Model pickers and run cards use these marks; source group icons do not stand in for a model. Node identities in chat headers, messages, sidebars, search results, mentions, settings and node selectors always use `NodeAvatar`, not the model mark.

`public/providers/manifest.json` and `NOTICE.txt` retain provenance and identification-only trademark notices. The Grok SVG is from LobeHub/lobe-icons under its included MIT licence. A public node exposes no private model choice: its signature face uses only its public avatar, never an inferred model.

## Connector logos

`ConnectorLogo` and `lib/connector-logos.ts` are the shared brand renderer and resolver. Connections use the catalog API's `logo` key (falling back to its ID for older responses), not the display name. Native connector tools and catalog MCP tool names use the same assets in completed replies, live tool chips and approval cards. Generic Ensemble tools stay generic; `apps_search` does not identify a service, so it keeps its wrench. Custom MCP names, including ones named after a vendor, are never treated as proof of that vendor's identity.

Assets are local under `public/connectors/`, reused from Ensemble's brand library with per-image provenance in `manifest.json` and licences/trademark attribution in `NOTICE.txt`. Wispr Flow and Zotero use real vendor marks rather than the Hub library's older placeholder lettermarks. This does not add integrations: the API catalog still controls what can be connected.

Tiles have fixed dimensions and contained, unmodified aspect ratios. A neutral white backing keeps black and coloured marks readable in both themes; small chat marks use 16 px tiles and connection rows use 36 px. Adjacent connection names make row logos decorative; standalone/tool logos have accessible names. Unknown logos use initials, custom MCP and CSV use explicit generic icons, and failed image loads retain the same tile with an accessible "logo unavailable" fallback. Branding does not replace connection status text, approval controls or tool-failure indicators.

## The model picker

One picker everywhere a model is chosen: new nodes, new nodes in a crew, and the node's settings. Groups: **Included with Ensemble** (Everyday and Step-up, with relative credits), **Your API keys** (per provider), **Your AI plans on ‹computer›**. The bootstrap carries the included models, so the picker opens at once; own keys and AI plans come from `/api/node/models` when it opens. A filter box appears for long lists, and the server's problems show at the bottom.

## Attachments

Both composers (a conversation's and the start page's) take files (`components/chat/attachments.tsx`, rules in `lib/attachments.ts`):

- **Adding:** the paperclip opens **Upload from this computer** and **Choose from Files**. Files can also be dropped on the composer (it shows "Drop to attach" while files are held over it; a file dropped elsewhere on the page is ignored, so the draft is never lost) or pasted. A picture that comes with copied rich text (the clipboard also has HTML with text in it, or RTF, as Word, Excel and web pages add) is ignored; a pasted screenshot is named "Pasted image ‹date› ‹time›".
- **Upload:** a file from the computer goes to the person's Ensemble Files at once (`POST /api/documents`, `summarize: false`) with real progress, before the message is sent. A file larger than the server keeps (`usage.maxFileBytes` from `GET /api/documents`: 25 MB on the hosted plan) is refused before it is read; any other refusal (a program, an empty file, quota) shows the server's own words.
- **Choose from Files:** the person's Files, newest first, searchable by name (`GET /api/documents?q=`). Each row shows kind, size and the date and time it was added, so files with the same name can be told apart. Picking one attaches it without uploading again; picking it again takes it off.
- **The shelf** above the text box has a chip per file: a thumbnail for pictures from the computer (a local preview), name, size, and while uploading the percentage, a progress bar and **Cancel**. Ready files have **Remove** (the file stays in Files). A failed upload shows why, with **Retry** and **Remove**. Up to 8 files per message; the same file is not added twice; a note says what was left out.
- **Sending** waits while a file uploads or after one failed, and says so next to the paperclip. A message may be files only. The paperclip's hint says who can read them: in a DM or crew, the nodes read the text of documents and see pictures when their model reads images; in a room with other people, nodes read files only from their own owner's messages, and others see a file's name but cannot open it.

## Messages and cards

- **Your messages** sit on the right in a gold-tinted bubble; Only‑me ones are violet with a lock.
- **Node messages** sit on the left with the node's signature face and name; someone else's node retains its owner label. Repeated handles are omitted from message headers. Markdown subset: headings, lists, code, quotes, bold, links (bare and `[label](address)`); known `@handles` are highlighted.
- **Records by title.** A node names Ensemble records by title, never by id (`lib/entity-text.ts`, the same rules as Ensemble's [docs/11 §4.1](https://github.com/ensemblework/ensemble/blob/main/docs/11_HOW_THE_ASSISTANT_WORKS.md#41-records-by-title-ids-for-machines)). A record link (`[@Draft brief](ensemble://task/…)`) shows its label and opens the record in Ensemble; a room opens here. A bare id of a record the message names (its `data.refs` and its tool chips' `refs`) shows as that record's title, linked; records with the same title get their kind, due date or a number. An id or record link in brackets right after the record's own title ("Expire Needs Me requests when their task ends (ensemble://task/…)") turns those words into the link, whether they are the whole title or its first clause; the title is never shown twice. On cards (briefs, reports), a record link nobody named shows as its kind, linked ("(task)"). Unknown ids, code, quotes and links stay as written, ids stay when someone in the turn asked for them (`data.showIds`), and what people write is never changed. Conversation previews, pins, reply quotes and Copy read the same way (`readableBody`). Text being written holds back a half-written id, using the turn's `refs` frame and its tool calls.
- **Code blocks** show the fence's language and a copy button above the code, which scrolls sideways instead of wrapping, also on a phone (`components/chat/code-block.tsx`).
- **Message actions** appear on hover or focus, or after a long press on a phone: react (the eight reactions), reply, copy, pin or unpin (only messages everyone in the room can read), delete (your own). Reactions show under the message with counts; yours are highlighted and the tooltip names who reacted.
- **Replies** quote the original above the message; the quote goes to it. While you reply to a private message, the composer is Only me.
- **Deleted messages** read "Message deleted".
- **Files on a message** (`components/chat/file-chips.tsx`) sit under its words as chips with kind, name and size. Your own link to the file in Ensemble's Files (`/files/:id`, new tab), and your pictures show a thumbnail read with your session (`GET /api/documents/:id/original`) once the chip is near the screen. Someone else's show only the name, kind and size with a lock; the tooltip says only that person can open it and your nodes see its name only. A message with only files previews as "📎 name" or "📎 3 files" in lists, pins and quotes.
- **Media from a node** (`data.media`): screenshots and videos a node sends with its message show in the same gallery as [evidence](#evidence), inside the message. A message with only media previews as "📎 2 pictures, 1 video".
- **Not sent:** a message the server refused stays with its reason, **Retry** (the same words, files and clientId, so nothing is uploaded again and the server keeps one copy) and **Edit** (back into the composer with its files, and its reply when that message is loaded).
- **Tools a reply used** fold into one line under it, "Used 4 tools · Search tasks, Read page, Assign to agent +1 · 1 failed", which opens into the tool chips: what the node did in Ensemble ("Create tasks · Added “Draft brief”."), each linking to the item in the Hub. A reply that used one tool shows that chip alone. They are shown only where nobody else reads.
- **Approval card** (owner-only): "@node wants to do this for you" with each held call as Ensemble describes it, by record titles, keeping its line breaks (pick some with checkboxes when there are several) → Approve / Discard; "@node wants to start work on your computer" with the agent, place and message → Start it / Discard; or "Post this in “Launch” for you?" with an editable draft → Post / Discard. States: Waiting for you, Applying…, Approved, Partly applied, Posted, Discarded; errors keep the card pending.
- **Secret card** (owner-only, also in Needs me and the Hub's Needs me): "@node needs a secret: NAME" with why, a password box ("Paste NAME"), Save to ‹computer› and Decline. The value is sent once and never shown again; the card then reads "Saved on ‹computer›. Runs there get it as $NAME." Errors (computer offline, no answer) keep the box open.
- **Plan card** (`components/chat/plan-card.tsx`, rules in `lib/plan.ts`): a lead's plan for its crew, as Ensemble projects its mission. Its opening words, "Plan" with its status and Stop (only while it runs, after a confirm), the goal, then the requirements ledger and one row per step. A routine's run (`data.routine`) has a small chip in its header, "Routine · Morning summary", which opens the routine in Routines; its card is not in the chat ([Routines](#routines)).
  - **Status:** "2 of 4 done" while it runs, then Planning, Reporting, Succeeded, Partly done, Failed or Stopped. A plan from before outcomes that ended "done" still reads Done.
  - **Requirements:** each requirement the owner asked for, with Open, In progress, Accepted, Failed, Deferred or Cancelled, and a line such as "3 of 5 accepted · 1 failed". Show criteria lists their acceptance criteria (optional ones marked). Deferred ones say why.
  - **A step's row:** the node's face and handle, the step's kind and who does it ("Verify · agent session", "Write · on its own"), whether it ran (Waiting, Working, Done, Blocked, Skipped, Stopped, or Finished when it has a verdict) and what came of it (Pass, Fail, Blocked, Unverified), the brief on one line, and the report or the live progress. A waiting step that an earlier failed, blocked or unverified step holds reads **Held**, "held by @builder" (Ensemble names that step by its id; the card shows its handle, and works it out from the steps before when the id is not on the card); otherwise "after @builder". A repeat shows "Attempt 2 · repair" or "Attempt 2 · retest". The row also counts its agent runs and evidence.
  - **Open, a step shows** its whole brief (record links by kind), the requirements it covers (linked to the ledger), the settings it asked for, its report, its attempts (each with outcome, its checks with verdict and detail, and the commit or content hash it built or tested), its [evidence](#evidence) and the agent runs it started, each a run card. Those run cards are not in the timeline, the conversation's preview or its unread count.
  - **Work card:** a node's own piece of work (`kind: "self"`, one step) is one compact block: "Work", its kind and status, the title, the live progress or result, and Details with the brief, attempts, evidence and runs.
- **Run card** (`components/chat/run-card.tsx`): a run on your computer, shown like a coding agent's own app. A run in an agent session is that session's card.
  - **Status line:** title (an update to a run reads "Update: ‹title›"), status pill and, while it runs outside a session, **Stop** (after a confirm; only for the person whose computer runs it). Under it the engine (Claude Code, Codex, Cursor, GitHub Copilot and Ensemble's other engines, or Ensemble's agent; before the job is read, the session's agent), the model, the thinking level, the computer, the time so far (ticking while it runs) and the attempt when it is a repeat. Then the latest progress line, or for a run the node queued in a session "it starts when the run before it ends", or for one a newer message took over (pill Updated, Replaced or Stopped) what happened to it.
  - **What the agent was told** (`data.told`): a run Ensemble started straight from a plan step has the packet it compiled for the agent (Goal, Your part, Constraints, Inputs, Who you are, Report), folded under the status line and shown with its parts as small labels. On the run going on in a session it is the session's own "What it was told" instead, so it shows once. A run that is Ensemble asking the agent once for the result it did not report (`data.reportAsked`) reads **Asked for its result**.
  - **Settings** (`data.settings`, `components/chat/session.tsx`): "Settings · as asked", "not as asked" or "not reported by the engine" opens what was **requested**, what was **resolved** (sent to the engine) and what the engine **observed** (reported), side by side; a setting that changed on the way is marked. A table on wider screens, one block per setting on phones.
  - **Session** (`data.session`, only on the run going on): the session's status, "Now:" what it is doing (with "What it was told": the card's packet when it has one, else the session's prompt), where it runs, and its queue in order. A card's `data.session.agent` is the agent's name and `agentId` its id; `GET /api/node/sessions/:id` has its id in `agent` and its name in `agentName` (`sessionAgent` in `lib/session.ts`): names are shown, ids decide. For the session's owner: Move earlier, Move later and Cancel on each queued message, and **Steer…**, **Queue…**, **Stop and send…** and **Stop** (keep or drop the queue). They act at once, through the same code as the node's own session tools, so the node always knows. Edits show at once; when Ensemble refuses one, the queue goes back and its words show in the card. A queued run says its place in line and can be cancelled.
  - **Needs you:** the run's own cards from Ensemble's Needs me (`detail.jobId` is this run) and its run approvals, one at a time ("1 of 2"). A permission shows its command with Allow once and Deny, plus Allow for this run when the run is not on a paired computer (a paired computer takes answers from the web once only, and a push is confirmed each time). A question shows its options with the recommended one marked, a box for your own answer when the agent allows one, and "Skip, let the agent decide". Risky ones ask to confirm first; ones that only that computer may approve offer Deny here. The same answers work on the Needs me page (`components/decision-answer.tsx`). "Answer it in Needs me" shows only when the run waits on something not listed here.
  - **Work log:** "Working · 23 tool calls" (or "Worked for 4m 20s") opens the engine's trace (`components/chat/work-log.tsx`, `lib/work-log.ts`). Consecutive tool calls fold into one line ("Read 1 file, ran 2 commands, edited 1 file") with their time and failures; the group the run is working in stays open. Each call has an icon for its kind (command, edit, read, search, web, MCP tool, question, subagent, thinking), its command in monospace or its target, its duration, and a red mark when it failed; it opens to the command (with copy), the lines removed and added, the input and the output. Thinking stays folded to its first line. The engine's own messages and milestones (asked you, restarted, decided on its own) sit between groups. The newest 12 items show first; "Show earlier" adds 30 at a time.
  - **Report** (`data.report`): what the worker reported, in a block of its own: Report with its outcome (Done, Pass, Fail, Blocked and why), "2 of 3 checks passed · 1 failed", each check with its verdict and detail, the commit it built or tested, and links it gave. A run with a report shows it instead of the free summary.
  - Then its [evidence](#evidence), the files the run changed with +/− counts, the summary (Markdown) or the error, and "Open the task in Ensemble" for a run on a board task (work a node runs on its own has no board task).
- **System lines** (joined, left, brakes) are centred and muted.

### Evidence

Files a run attached (`data.evidence` on its run card: screenshots, videos, traces, reports, logs) show as a gallery (`components/chat/evidence.tsx`, rules in `lib/evidence.ts`) on the run card, and on its plan step, which gathers its runs' evidence. A node's media (`data.media`) uses the same gallery in its message.

- **Pictures** (PNG, JPEG, GIF, WebP, AVIF) show as thumbnails read with your session (`GET /api/node/evidence/:id`) once they are near the screen, and only when the bytes that come back are such a picture. They open in a lightbox: the picture large, its caption, "2 of 5", Download and Close. Arrow keys move, Home and End go to the first and last, Escape closes and focus goes back to the thumbnail; on a phone a swipe moves.
- **Videos** play in a player in place (and larger in the lightbox). One that cannot be read becomes a download.
- **Everything else**, and every active format whatever its kind says (HTML, SVG, XML, scripts, PDF), is a download row with kind, size and caption. Nothing active is ever shown in the page.
- A caption shows under each piece, and "For: ‹requirement›" when it is for one of the plan's requirements, linked to the ledger.

### Helper threads

A helper's room (`kind: "task"`) is not in the conversation list (`lib/threads.ts`). Under the message that brought the helper in, a chip reads "@scout, helper of @lead · working · 4 messages" (or quiet). It opens in place to the helper's conversation, read only, with what it is writing now and "Open the helper's room". Reading it there marks the room read. A link to a helper's room still opens it, read only.

- **Where it shows.** Ensemble's room view says whose helper it is and where its parent was asked (`helper`: the parent, the helper, the origin room, and whether it was asked privately). The thread goes in that room, under the parent's reply whose `node_helper` call names the helper or its room. Rooms from before `helper` are read from their members, and their threads go to the parent's direct chat. A helper whose message is not loaded, or does not say, is under Helpers in the "Working on" strip and opens in a side panel.
- **Asked privately.** A helper asked for in your private thread of a room (`originPrivate`) shows only under a private message, and its chip carries the lock and the private tint, here and in the strip.
- **What it may do.** The thread's header says it: "Can read", "Can run sessions" or "Can use the computer" (the helper's `autonomy.grant`), and that it reports to its parent. The helper's room settings say the same.
- **Keep as a node.** In the thread's header and the room's settings, after "Keep @scout as a lasting node? It gets its own chat." (`POST /api/node/nodes/:id/promote`). The helper leaves its parent, keeps its charter and memories, and its own chat appears in the list. The thread then reads "Kept as a node" with "Open its chat"; its room stays as history, and deleting that room leaves the node.

### Working on

Under a conversation's header, a one-line strip lists what is working there, from what is already loaded: your live plans and pieces of work ("2 of 6 done", the work's progress), routines' runs that report here, your agent sessions with a live run, one per session ("Running · 2 queued"), and helpers that are working. A chip opens its card in the timeline; a routine's run, whose card is not in the timeline, opens its card in a side panel. Quiet helpers whose message is not on screen follow under Helpers. The strip scrolls sideways on a phone and is gone when nothing runs.

### Stopping work

While your work runs in a conversation (a live plan or work card, a live agent run, or a reply being written), its header has **Stop**; More always has "Stop this conversation's work". Both, and the composer's stop button while a node writes, call `POST /api/node/rooms/:id/stop`, which stops your nodes' replies, plans and their runs there. They ask first only when plans or runs are going on; stopping a reply being written does not ask. The result shows in a note ("Stopped. What was changed so far stays." or "Nothing was running here."). A plan or work card has its own Stop while it runs (`POST /api/node/plans/:id/stop`, after a confirm), and a session's Stop keeps or drops its queue.

## Routines

A routine is work a node does on its own: on a schedule, when tasks or pages change in Ensemble, or when a webhook calls (Ensemble's [docs/35 §6.5](https://github.com/ensemblework/ensemble/blob/main/docs/35_ENSEMBLE_NODE.md#65-routines)). `/routines` lists them all by node (`components/routines.tsx`, rules in `lib/routines.ts`), from the sidebar and Settings; a node's settings list its own, with New routine for that node.

**The form** opens in a drawer (in a node's settings, in place) and fits a 390 px phone:

| Field | What it takes |
| --- | --- |
| Title | Up to 120 characters |
| Node | One of your nodes, never a helper. A routine's node does not change once it is made |
| Reports in | The node's chat (the default) or one of your crews it is in: only where you read alone |
| What it does | **Instruction** (the default): work the node does itself. **Saved plan (advanced)**: a plan as a lead makes one (`node_plan`: goal, requirements, constraints, steps), as JSON, run as a plan in the node's crew |
| When | **Schedule**: every day at, weekdays at, every week on ‹day› at, every month on ‹day› at, every hour at :mm, or a custom cron, in a time zone (the browser's by default; search by city or region). **Event**: a task or a page changing, only for the actions ticked (task: created, updated, moved, assigned, deleted, agent run; page: created, saved, deleted; none ticked: any change), in your own space or one you name, gathered for 60 seconds by default. **Webhook**: its own address and token |
| Tell me | Always post the result · Only when something needs me · Never post (keep a log) |

- **Schedules.** A preset becomes a five-field cron in the browser and reads back before saving ("Every Friday at 16:30 (Europe/London) · 30 16 * * 5"); once saved, the list shows Ensemble's own words for it. A cron that is one of the presets opens as that preset. A day of the month after the 28th notes that shorter months are skipped.
- **Problems** show when Create or Save is pressed, by their field, and focus goes to the first; a plan's JSON and a cron are checked as they are typed. Ensemble checks everything again, and its refusal shows above the buttons.
- **A webhook's token, once.** Making a webhook routine, giving it a new token (New token, after a confirm: the old one stops working) or turning a routine into a webhook shows its full address (the API's origin and the routine's path) and its token once, with Copy and a `curl` example: "Copy the token now. You will not see it again." The token is never kept in the browser; afterwards only the address shows.
- **Runs.** Run now starts a run whatever the trigger, paused or not, and opens History with it first. History lists the newest 50: Waiting, Starting, Skipped or Failed (with why), then the mission's status (Running, Reporting, Succeeded, Partly done, Failed, Stopped), the trigger (On schedule, On a change, Webhook, By hand), when, and what it gathered ("3 changes"). A run's card is not in the chat (its message's `planId` is the routine's id), so **Open** reads it (`GET /api/node/messages/:missionId`) and shows the plan or work card in a drawer, live, with its Stop while it runs, the agent runs from its conversation, and a link to that conversation.
- Routines are read again every 30 seconds, and at once when a routine's run card changes on the event stream.

## Live behaviour

One EventSource per tab (`/api/node/events`, with credentials). `node.message` / `node.message.updated` merge into every loaded list by id or clientId and update the sidebar preview immediately. Reactions and old edits do not move a conversation or increment unread counts. `node.status` drives the status halo and typing preview. `node.frame` (owner only) streams text, tool names and known records (`refs`); `lib/live.ts` buffers text once per animation frame for that room, while sidebar busy state changes only at start/stop. `node.room` refreshes the list and pins; `node.invite` refreshes invites; `node.needs` re-reads pending cards immediately (60-second poll fallback).

The timeline follows new messages and resized/streaming content only while already at the bottom. Reading earlier work keeps its position and offers a counted jump-to-latest. Older-page loads preserve the anchor. Pending sends and their confirmed copies share the same clientId render key, avoiding duplicate bubbles or repeated entrance animations. Only new arrivals get a short entrance, disabled with reduced motion.

Unsent text and its Only me state survive switching conversations in tab memory, scoped by account and room; they are not written to browser storage. Attachments and reply targets are not part of these text drafts. Read updates are debounced per room, so switching chats cannot cancel the previous room's update. Bootstrap refreshes preserve newer live previews and read markers; failed read writes restore the prior marker and report an error.

Run cards read the job when visible and every 2.5 seconds while active and visible/open; trace steps load only while the work log is open. Ended runs are read once. A changed run message refreshes both immediately. The session of a live run is read (`GET /api/node/sessions/:id`) while its card is on screen, every 2.5 seconds, and again when its card changes. Evidence pictures are read once per page and shared by thumbnails and the lightbox. Reconnects refresh open messages and Needs me, retaining earlier pages.

## Links

Links that leave Node (Ensemble, ensemblework.com, vendors, links in messages) open in a new tab; a link to a room opens here. Sign-in with a provider stays in the same tab, because it returns to Node.

## Responsive and installable

Phones open Chats as a left sheet; selecting a conversation closes it and opens that group's timeline, not a separate form. A conversation uses one header with back-to-chats; other pages retain the global menu/Search/Activity bar. From 768 px the collapsible sidebar is fixed; from 1024 px Activity can be opened on the right. Drawers trap keyboard focus, close on Escape/backdrop and restore the opener. The web manifest makes it installable to a Home Screen (start URL `/chat`). `public/sw.js` is ready for web push (v1).

The conversation scrolls independently of its header and composer. On phones the shell and drawers follow the visual viewport when the keyboard opens; the composer includes the bottom safe area. Form fields use at least 16 px text to avoid Safari's focus zoom. Long names, model/computer metadata, answers and message text wrap within their cards, while fenced code and tool output retain their own horizontal scrolling. The model menu stays inside the phone viewport. Drawers scroll their own content and keep Close in a sticky header.

`InfoTip` makes longer model/permission explanations available on hover, focus or tap, without permanent paragraphs. Errors, privacy labels and approval controls stay visible.

## Browser regression

`e2e/chat-ui.mjs` runs a stateful local API/SSE fixture, never a hosted account or model. Start `pnpm dev` on an unused port, then run it with `NODE_WEB`, `CHROME_PATH` and, when Playwright is supplied externally, `PLAYWRIGHT_MODULE` (the absolute module entry). `NODE_CHAT_SHOTS` optionally saves evidence outside the repository. It exercises five widths, dark/light themes, cross-kind recency, rail persistence, group opening, streaming/scroll anchoring, optimistic sends and private text-draft restoration.

`e2e/runtime-cards.mjs` runs the same way and covers the runtime cards at phone and desktop widths: a plan card with held steps, attempts, checks and the ledger (and the §4.11 brief shown once, on one line), a contract 1 card and a work card; the session card's settings, queue moves (one refused), cancel, Steer and Stop, and the packet it was told; a run asked for its result; evidence (SVG and HTML only as downloads, the lightbox's keys and focus); a node's media; the room's Stop and the "Working on" strip, with a routine's run opening its card; and a helper thread in place of its room in the list, what the helper may do, and keeping it as a node.

`e2e/routines.mjs` covers Routines at 390 and 1280 px: the list by node, pausing and resuming, a scheduled routine made from presets in a searched time zone (its problems first), a webhook routine's token shown once and a new token, Run now, a run's card in a drawer with what its agent was told, editing, deleting, a node's routines in its settings, and a card's link to its routine.
