# Ensemble Node — 2026 Landscape Research Report

*Compiled 2026‑10‑19 from six parallel deep-research passes, each cross-checking official docs, GitHub source, NVD/GHSA advisory APIs, and vendor pricing pages, plus independent spot-check searches on the most surprising claims. Legend: **✅** primary-source confirmed · **⚠️** partially verified/conflicting · **❓** rumored or secondary-source-only · **🚫** explicitly checked and found false.*

## A. Self-hosted / runs-on-your-own-machine agents

### A1. Personal agent daemons (the "OpenClaw" category)

| Project | Repo | Scale | Language | Notable security track record |
|---|---|---|---|---|
| **OpenClaw** (was Clawdbot → Moltbot → OpenClaw) | `openclaw/openclaw` | 392k★/82k forks | TypeScript | 2 NVD CVEs, **CVSS 8.6–8.8**; 40,214 exposed instances found by SecurityScorecard |
| **Hermes Agent** (Nous Research — distinct from the "Nous Hermes" LLM weights) | `NousResearch/hermes-agent` | 255k★ | Python | 2 NVD CVEs, CVSS 5.0–6.3, lower severity, "Deferred"/vendor-unresponsive status |
| **ZeroClaw** | `zeroclaw-labs/zeroclaw` | 33k★ | Rust | No CVEs found; WASM-sandboxed plugins (strongest plugin isolation of the group) |
| **NanoClaw** | `nanocoai/nanoclaw` | 31k★ | TypeScript | No CVEs found; Docker-per-agent isolation, explicit critique of OpenClaw's shared-process model |

**OpenClaw architecture** ✅ (`docs.openclaw.ai`):
- **Gateway**: one always-on Node.js process, single multiplexed port (default `18789`) serving WebSocket control/RPC + HTTP APIs + Control UI. Auth via token/password or trusted-proxy mode. Protocol formally specified in TypeBox schemas (`openclaw/openclaw:packages/gateway-protocol/src/schema.ts`).
- **Channels**: 20+ integrations (WhatsApp via Baileys/QR login, Telegram, Slack, Discord, iMessage via a stdio JSON-RPC helper, Signal via `signal-cli`, Matrix, Teams, etc.), each tagged bundled/official/external plugin.
- **Skills**: a skill = directory with `SKILL.md` (YAML frontmatter + markdown), 7-level load-order precedence (workspace → project → personal → managed → self-authored → bundled → plugin), distributed via ClawHub (`clawhub.ai`).
- **Heartbeat/cron**: unified "Automations" scheduler; heartbeat is a system-owned ambient-monitor automation (default 30 min interval) distinct from user cron jobs.
- **Memory**: plain Markdown on disk (`USER.md`, `MEMORY.md`, daily `memory/YYYY-MM-DD.md`, optional `DREAMS.md`) — explicitly "no hidden state." Can import memory from Codex, Claude Code, and Hermes.
- **Multi-agent routing**: multiple isolated agent personas per Gateway, each with its own workspace + per-agent SQLite; a "binding" maps a channel account → agent. **Default config shares session visibility across all agents on a Gateway** (`tools.sessions.visibility: "all"`) — a notable trust-model gotcha.
- **Node/device pairing** (the key mechanism for your design): **direct-connection model, no vendor relay.** A setup code is a base64 JSON payload containing the Gateway's own `ws://`/`wss://` URL + a 10-minute single-use bootstrap token; the phone/desktop client scans a QR code and **connects directly** to that address. Device identity uses a pubkey/signature handshake. For remote (non-LAN) access, docs explicitly recommend Tailscale Serve/Funnel or a self-managed reverse proxy/SSH tunnel — **OpenClaw does not operate its own hosted tunnel.**
- **Security**: explicitly scoped as **"one trust boundary per gateway"** — not designed for mutually adversarial users sharing one agent. Two NVD CVEs confirmed: **CVE-2026-25253** (CVSS 8.8 — Control UI auto-connected to an attacker-supplied `gatewayUrl` query param and sent the stored auth token, chained with a WebSocket Origin-validation bypass for a documented 1-click RCE; [GHSA-g8p2-7wf7-98mq](https://github.com/openclaw/openclaw/security/advisories/GHSA-g8p2-7wf7-98mq), [writeup](https://depthfirst.com/research/1-click-rce-to-steal-your-moltbot-data-and-keys)) and **CVE-2026-28456** (CVSS 8.6 — unsanitized hook-module path passed to Node's `import()`). SecurityScorecard found **40,214 internet-exposed instances** (63% vulnerable, 12,812 RCE-exploitable) via Shodan, reported by [Infosecurity Magazine](https://www.infosecurity-magazine.com/news/researchers-40000-exposed-openclaw/). A related platform, "Moltbook" (an agent social network), leaked 1.5M agent auth tokens via a misconfigured Supabase instance ([Wiz](https://www.wiz.io/blog/exposed-moltbook-database-reveals-millions-of-api-keys)). Cisco found a malicious third-party skill performing silent data exfiltration. China restricted enterprise/government use (March 2026).

**Hermes Agent** ✅ — same category, architecturally convergent (identical `SKILL.md` format, nearly identical pairing-code design cited to OWASP/NIST) but with one explicit, stated difference: **"the only security boundary against an adversarial LLM is the operating system... not the approval gate, not output redaction, not any pattern scanner"** (`SECURITY.md`) — i.e., Hermes documents its in-process safety features as non-boundaries, requiring an external sandbox (Docker/SSH/Modal/Daytona) for real isolation. Remote-dashboard access is **inbound-connection** (bind `hermes dashboard` to a non-loopback address; fails closed without auth configured) rather than OpenClaw's QR-code direct-dial model — functionally similar (both require the host to be network-reachable) but structurally mirrored. A separate, explicitly **"EXPERIMENTAL"** relay subsystem does use an outbound-dial-to-hosted-connector pattern, but only for specific platform webhook ingestion (e.g., Discord Interactions), not general dispatch.

**Implication for Ensemble Node**: both flagship projects in this category use **direct-connect pairing (QR/setup-code with embedded address + bootstrap token), not a vendor-run relay**, and both treat "the OS is the only real sandbox" as their honest security position. Their worst incidents came from **trusting a client-supplied URL/token on page load** and **unauthenticated exposure to the public internet** — both single boundary-crossing mistakes, directly relevant if Ensemble Node's local daemon exposes any HTTP/WS control surface.

### A2. Remote-dispatch coding agents

All five major coding-agent products have converged on the **same two-track architecture**: (1) a default vendor-hosted cloud sandbox, and (2) an explicit **"bring your own compute"** track where a customer-run worker makes an **outbound-only** connection to the vendor's control plane and claims queued work from it — no inbound ports, no tunnel, no VPN.

| Product | Local/self-hosted dispatch mechanism | Pairing/auth | Sandboxing |
|---|---|---|---|
| **Claude Code** (Anthropic) | **Self-hosted environments** (public beta): a runner registers, gets a runner token, then **long-polls** for sessions over HTTPS; each poll refreshes a lease (lapses after ~60s if polling stops). "Anthropic never connects into your network." [docs](https://code.claude.com/docs/en/self-hosted-environments) | Shared-secret "environment key" (shown once) → rotatable runner token, same shape as a GitHub Actions self-hosted runner | Local CLI: bubblewrap (Linux)/Seatbelt (macOS), open-sourced as [sandbox-runtime](https://github.com/anthropics/sandbox-runtime); cloud: per-session VM, git ops proxied through a credential-scoping service so GitHub creds never enter the VM |
| **OpenAI Codex / "dots"** | Cloud = managed "environment"; local-connect is a **ChatGPT-desktop-app-as-daemon** model ("dots" can "Connect your computer" — desktop app must stay open/online); no named transport in official docs | ChatGPT OAuth sign-in (required for cloud); API keys explicitly **do not** enable local-computer access — only a workspace sign-in + admin toggle does | Sandbox mode (filesystem/network scope) × approval policy (when to prompt), independently configurable; network off by default even locally |
| **GitHub Copilot cloud agent** (renamed from "coding agent" ~Apr 2026) | Ephemeral **GitHub Actions**-backed container by default; **officially supports GitHub Actions self-hosted runners** for the cloud/cloud agent. Separate "Remote Control" of local Copilot CLI sessions **explicitly documented as polling**: *"Remote commands are polled by Copilot CLI from GitHub... all shell commands happen on your machine."* [docs](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-remote-control) | Standard GitHub OAuth/App install; Copilot gets its own scoped token per run, not the invoking user's PAT | Ephemeral Actions container, minimized permissions, can't merge its own PR; local "sandbox" mode in the Copilot desktop app restricts filesystem/network for on-machine sessions |
| **Cursor Cloud Agents** (renamed from "background agents" ~Feb 2026) | **Self-Hosted Machines**: *"Cursor keeps the agent loop (inference/planning); your code, secrets, and tool execution stay on your machine... Cursor sends tool calls to it over an outbound HTTPS connection... No inbound ports or VPN required."* [docs](https://cursor.com/help/ai-features/self-hosted-machines) | Personal API key or team service-account key (static bearer token); can also mint short-lived **OIDC JWTs** from a local socket for cloud-provider auth instead of long-lived secrets | Managed Cloud Agents run on **Firecracker microVMs in a separate AWS account**; commits HSM-signed (Ed25519) |
| **Devin** (Cognition) | **Outposts**: *"The worker opens an outbound connection to Devin's cloud and watches the outpost's queue... Workers only need outbound HTTPS access. No inbound ports, public IPs, or VPN tunnels required."* [docs](https://docs.devin.ai/cloud/outposts/overview.md) | One-time-displayed Outpost token (`devin worker start --outpost=<name> --token=<token>`); separate Service User API Keys vs Personal Access Tokens for the general API | "Brain" (stateless planning, always cloud) + "Devbox" (execution sandbox, location depends on deployment: shared cloud / dedicated VPC via PrivateLink / Outpost) |

**Confirmed CVEs** (via NVD/GHSA APIs directly): Claude Code — 4 confirmed GHSAs (sandbox escape via git-worktree path confusion, CVE-2026-55607; pre-approved `huggingface.co` allowlist exfil side-channel, CVE-2026-54316; trust-dialog bypass via worktree spoofing, CVE-2026-40068; Cowork auto-exec file-type gap). Cursor — 3 confirmed CVEs (sandbox escape via unprotected `.git` hooks, CVE-2026-26268; agent-terminal working-directory manipulation, CVE-2026-50548; unauthenticated local endpoint reachable from browser-rendered content, CVE-2026-61613). GitHub Copilot CLI — 1 confirmed (shell parameter-expansion RCE via prompt injection, CVE-2026-29783). OpenAI Codex — 1 confirmed (zero-click image-render exfil via prompt injection, CVE-2026-14898). **Devin — no NVD/GHSA CVE found** in this research (notable asymmetry vs. the other four — could reflect better engineering, smaller install base, or less researcher attention; can't distinguish from available evidence).

**Dominant exploit pattern across vendors**: prompt-injection-driven sandbox escapes via **git internals** (worktrees, hooks, `.git` config) hit both Claude Code and Cursor independently — worth specific defensive attention if Ensemble Node drives git-based coding agents.

**Implication for Ensemble Node**: the industry has independently converged, three times over (Anthropic, Cursor, Devin, and GitHub via Actions runners), on **"local worker process opens an outbound HTTPS connection, authenticates with a pre-shared/rotatable token, and polls or long-holds a connection to claim queued work from a cloud queue."** This — not an inbound WebSocket tunnel — is the validated pattern to copy for your local-CLI-daemon architecture. A **separate** "remote control/mirror" pattern (session actually starts locally, web UI only views/steers it) exists at Anthropic, GitHub, and OpenAI, but that's a different feature (mirroring) from dispatch (assigning new work).

## B. Multi-agent group chat & delegation patterns

### Framework status and core mechanisms

| Framework | Status (2026-10-19) | Who-speaks-next | Delegation style |
|---|---|---|---|
| **AutoGen** (Microsoft) | ✅ **Archived** — README states *"no longer actively maintained... no bug fixes, security fixes, new features, or support"* ([repo](https://github.com/microsoft/autogen)) | `RoundRobinGroupChat` (modulo rotation); `SelectorGroupChat` (LLM picks, excludes previous speaker by default-off flag, retries on invalid output, falls back to previous speaker/first participant); `GraphFlow` (conditional graph edges) | `Swarm` pattern — explicit handoff via `HandoffMessage.target` |
| **Microsoft Agent Framework** (MAF) — AutoGen's successor | ✅ 1.0 GA ([docs](https://learn.microsoft.com/en-us/agent-framework/overview/)) | `SequentialBuilder` (round-robin), `ConcurrentBuilder` (fan-out); **LLM-driven selector and handoff are still roadmap-only**, not yet shipped | `MagenticBuilder` (planner/orchestrator-driven); typed-edge `WorkflowBuilder` for explicit routing |
| **CrewAI** | ✅ Current, active | N/A (task-order, not speaker-order) for sequential; manager LLM picks via tool call for hierarchical | **Only tool-call delegation** — `DelegateWorkTool`/`AskQuestionTool`, manager stays in control, **synchronous in-process call**, fuzzy-matches worker by free-text role name |
| **LangGraph/LangChain** | ✅ Current; `langgraph-supervisor` package **officially soft-deprecated** in favor of the "subagents" pattern (main agent calls workers as tools via `create_agent`) | `StateGraph` edges you define; `Command(goto=...)`/`Send(...)` for conditional/fan-out routing | Both **"Subagents"** (tool-call, manager retains control) and **"Handoffs"** (`Command` changes active agent — control transfers) are named, first-class, documented patterns |
| **OpenAI Agents SDK** | ✅ Current | Triage agent's handoff tool-call choice; `is_enabled` can dynamically gate which handoffs are even offered | **"Agents as tools"** (`Agent.as_tool()`, manager keeps control) vs. **"Handoffs"** (`handoffs=[...]`, specialist becomes active agent for rest of turn) — both named explicitly, with guidance on when to use each |
| **Claude Agent SDK** | ✅ Current | Claude decides via subagent `description` matching | **Only tool-call delegation** — subagents run isolated/backgrounded by default, return only a final message to the parent; no "takes over the thread" concept |
| **Slack / Microsoft Teams** | ✅ Platform behavior | **@mention-gating is the platform default**: Slack's `app_mention` event never fires for un-mentioned messages; Teams goes further — *"your agent doesn't receive a message... when someone replies to a message from your agent without @mentioning it"* ([MS Learn](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/how-to/conversations/channel-and-group-conversations)) | N/A — routing is done by the human via @mention, not software |

LangChain explicitly credits **OpenAI's vocabulary** ("handoffs") as the term it's aligning with — "agent-as-tool vs. handoff" is becoming cross-framework standard language, not framework-specific jargon.

### The 5 recurring problems — synthesis

**1. Who-speaks-next routing** — three strategies recur everywhere: *round-robin* (deterministic, cheap, can't adapt), *LLM-driven dynamic selection* (adapts to content, costs an extra model call, needs retry/fallback machinery to be safe — AutoGen's selector re-prompts on invalid output and falls back to a deterministic choice rather than looping), and *graph/rule-based routing* (fastest/most predictable, requires anticipating transitions upfront). Notably, **the whole industry's direction (MAF's Workflow vs. AutoGen's GraphFlow, LangGraph's explicit edges) is trending toward less implicit LLM routing in favor of explicit typed edges.**

**2. Manager/supervisor delegation** — a clean, consistent split: **tool-call delegation** (manager retains control; worker is "just a tool call"; CrewAI and Claude Agent SDK support *only* this mode) vs. **explicit handoff** (control genuinely transfers; OpenAI Agents SDK and LangGraph support both and give the same rule in near-identical language: *use tool-call delegation when a specialist helps with a bounded subtask but shouldn't own the user-facing conversation; use handoffs when routing itself is part of the workflow and the chosen specialist should own the rest of the turn.*) — **Direct mapping to your architecture**: human→private-worker-bot delegation is unambiguously tool-call/subagent style in every framework's vocabulary (workers report back, don't take over the shared thread); manager-bot↔other-humans'-manager-bots in the shared group chat is more of a handoff/peer relationship when "whose turn" should visibly move.

**3. Avoiding bot-to-bot infinite loops** — concrete mechanisms actually found in code/docs (not just handwaved): no-repeat-previous-speaker constraints (AutoGen); stall-detection + automatic re-planning, a materially different strategy from a hard cap (AutoGen Magentic-One / MAF's `max_stall_count`); hard turn/message caps as composable termination conditions; **platform-level mention-gating** (Teams: a bot doesn't even see un-mentioned replies to its own messages — this prevents the classic Bot-A↔Bot-B ping-pong *by construction*, with zero app code); and output-scanning for forged control tokens (Claude Agent SDK v2.1.210+ scans a subagent's final message for forged `<system-reminder>` tags before the parent reads it). **No framework researched implements semantic/content-based loop detection** (e.g., embedding-similarity repetition detection) — that appears to be something you'd have to build yourself.

**4. Turn budgets** — "turn" is **not a standardized unit** across frameworks, which matters if you're porting a number from one to another:

| Framework | Default | What's counted |
|---|---|---|
| OpenAI Agents SDK | `DEFAULT_MAX_TURNS = 10` (source-confirmed) | One LLM call (persists across handoffs) |
| LangGraph | `recursion_limit = 25` | One Pregel super-step (one synchronous wave of node activation) |
| AutoGen | **No default** — `max_turns=None` is legal/common, relies entirely on `termination_condition` | One full round (every active speaker responds once) |
| CrewAI | `max_iter = 20` | One ReAct tool-iteration **within a single agent's task** — not crew-wide |
| Claude Agent SDK | No numeric default found | Governed by subagent nesting-depth/concurrency/spend caps instead |

Recommendation surfaced directly from this research: define your own explicit turn unit (closest analog: AutoGen's "one round across all currently-active bots") rather than borrowing a number, because the frameworks fundamentally disagree on what's being counted.

**5. Human approval gates** — four distinct architectures: (a) **dynamic in-code pause** — LangGraph's `interrupt()` + `Command(resume=...)`, keyed on thread ID, can wait indefinitely (not just milliseconds); (b) **declarative per-tool policy with graded decisions** — LangGraph's `HumanInTheLoopMiddleware` (`approve`/`edit`/`reject`/`respond`) and Claude Agent SDK's 6-stage pipeline (`hooks → deny rules → ask rules → permission mode → allow rules → canUseTool callback`), settable **per-subagent**; (c) **request/response workflow primitive** — MAF's `ctx.request_info()`, built specifically because AutoGen's `Team` had *no* way to pause at all; (d) **post-hoc review only** — CrewAI's `Task(human_input=True)` reviews the *final* answer only, no mid-run pause (weakest option if you need "approve before a side-effecting action runs"). A notable gap: **none of the developer frameworks documented a simple "just send a message and it preempts an in-flight turn" UX** — the one place this *is* documented is **Grok Bot** (xAI/Cursor's agentic product, not the consumer Grok-on-X assistant — see caveat below): *"A direct message from you takes priority over background work and can redirect the current turn... Send 'Stop now' when work should end immediately"* ([docs.x.ai/grok-bot](https://docs.x.ai/grok-bot/chat-and-collaboration)) — arguably the most directly reusable idea for your "human present in a live multi-bot group chat" scenario.

**⚠️ Naming caveat**: `docs.x.ai/grok-bot` documents **"Grok Bot,"** a Cursor-integrated computer-use agent product (2–6 bots per group chat, @mention routing, admin-toggleable "Messaging Between Bots") — genuinely useful as a second multi-bot-group-chat reference implementation. This is a **different product** from the consumer Grok assistant inside X's group chats/DMs, for which no primary documentation could be found (official X help pages 404'd); treat any claims about "Grok in X group chats" as low-confidence/secondary-sourced.

**Slack/Teams rate limits** (platform constraints relevant if multiple bots are chatty in one room): Slack `chat.postMessage` ≈ 1 msg/sec/channel, Events API 30,000 deliveries/workspace/app per 60 min; Teams-specific per-bot rate limits were not found in documentation (likely enforced at the Bot Framework/Azure connector layer).

## C. Protocols

| Protocol | Boundary | Version (2026-10-19) | Governance |
|---|---|---|---|
| **A2A** (Agent2Agent) | Agent ↔ agent | **v1.0.1** (2026-05-28; v1.0.0 was 2026-03-12) | Donated by Google to the **Linux Foundation** (June 2025); as of **August 2026 moved under the Agentic AI Foundation (AAIF)**, a Linux Foundation sub-body dedicated to agent interoperability (alongside MCP) — technical-only governance change, specs/SDKs unchanged. 8-seat TSC (Google, Microsoft, Cisco, AWS, Salesforce, ServiceNow, SAP, IBM). [spec](https://a2a-protocol.org/latest/specification/) · [repo](https://github.com/a2aproject/A2A) |
| **MCP** (Model Context Protocol) | Agent ↔ tools | **2026-07-28** revision (current), superseding 2025-11-25 | Anthropic-originated, now broader multi-stakeholder governance (SEP process) |
| **ACP** (Agent Client Protocol) | App/daemon ↔ local coding-agent CLI | Wire protocol **v1 stable**; **v2 still explicitly labeled draft**; crate releases near-weekly (`v1.12.0`, 2026-10-16) | Moved from `zed-industries` into a dedicated **`agentclientprotocol`** org, co-led by Zed (Ben Brandt) and JetBrains (Sergey Ignatov) |
| **AG-UI** | UI ↔ agent | **1.0** (first release with a normative spec, vs. 0.x's implied-by-client-code behavior) | CopilotKit-originated; still shipping near-daily (releases through 2026-10-18) |

**A2A** ✅ — core objects, all cited to `a2aproject/A2A:specification/a2a.proto`: **Agent Card** (discovery doc at well-known URI `GET /.well-known/agent-card.json`; fields include `name`, `supported_interfaces` [multi-transport-per-agent], `capabilities` [streaming/push/extensions bools], `skills`, JWS `signatures`); **Task** (`id`, `context_id`, `status`, `artifacts`, `history`) with a 9-state `TaskState` enum (`SUBMITTED→WORKING→{COMPLETED|FAILED|CANCELED|REJECTED}` terminal, plus `INPUT_REQUIRED`/`AUTH_REQUIRED` interrupts); **Message** (`role`: USER/AGENT, repeated `Part`); **Artifact** (named output bundle of `Part`s); **streaming** via both SSE/gRPC-stream (`SendStreamingMessage`/`SubscribeToTask`) *and* async webhook push notifications for disconnected scenarios — both exist, for different cases. Auth models OAuth2/OIDC/API-key/mTLS on the OpenAPI 3.2 Security Scheme Object, including device-code grant (RFC 8628) for CLI-style agents. **Caveat**: A2A is pairwise client→remote-agent task delegation, not native N-party group chat — Ensemble Node would need its own room/group semantics layered on top.

**MCP** ✅ — the 2026-07-28 revision is a much bigger change than the original 2025-03-26 HTTP+SSE→Streamable-HTTP swap: it **removed protocol-level sessions entirely** (no more `Mcp-Session-Id`, no `initialize` handshake) and made MCP **fully stateless** — every request self-contained, routable to any server instance with no sticky sessions (confirmed via [official changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx) and independent web verification). Server-initiated requests (sampling, elicitation) were replaced by **MRTR** (Multi Round-Trip Requests) — an `InputRequiredResult`/retry pattern instead of a persistent bidirectional stream. OAuth 2.1 stack: Authorization Code + mandatory PKCE, RFC 8707 Resource Indicators (mandatory), RFC 9728 Protected Resource Metadata (mandatory), and a new preferred **Client ID Metadata Documents (CIMD)** mechanism replacing Dynamic Client Registration for client/server pairs with no prior relationship. **Implication**: build explicit version negotiation — a large fraction of currently-deployed MCP servers still speak the older, stateful 2025-era wire format.

**ACP** ✅ — modeled explicitly on LSP ("any editor ↔ any agent"); local agents run as **subprocesses over JSON-RPC 2.0/stdio**; remote (HTTP/WebSocket) agents are **explicitly still "a work in progress"** upstream — relevant caveat if your daemon needs to drive a coding agent non-locally. Flow: `initialize` → `auth/login` → `session/new`/`session/resume` → prompt loop (`session/prompt` → streamed `session/update` notifications → possible permission requests → optional `session/cancel`). **Adoption directly answers your question**: **Gemini CLI** implements it natively (`gemini --acp`); **Claude Code** via a Zed-maintained adapter (`zed-industries/claude-agent-acp` wrapping the Claude Agent SDK); **Codex CLI** via an ACP-org-maintained adapter (`agentclientprotocol/codex-acp`); plus Goose, GitHub Copilot CLI, Cursor, JetBrains Junie, OpenHands, Cline, and ~25 more clients/agents total. **Best current fit for "driving Claude Code/Codex/Gemini CLI programmatically from a daemon,"** with the caveat that you'd start with local subprocess-over-stdio and treat remote-driving as a custom extension.

**AG-UI** ✅ — a pure event-stream protocol (not JSON-RPC), explicitly positioned by its own docs as the **"3rd leg"** alongside MCP and A2A:

| Layer | Protocol | Purpose (AG-UI's own framing) |
|---|---|---|
| Agent ↔ User | AG-UI | connects agents to user-facing apps |
| Agent ↔ Tools/Data | MCP | agents to tools/workflows/data |
| Agent ↔ Agent | A2A | agents coordinating across distributed systems |

8 event families (Lifecycle, Text Message, Tool Call, State [JSON-Patch snapshot+delta], Activity, Subagent, Special, Draft) over SSE or (new in 1.0) binary HTTP+Protobuf. AG-UI explicitly documents "handshakes" with MCP and A2A so a UI client can transparently front an agent that's actually backed by either. Still CopilotKit-centric for first-party SDKs (React/Angular) but the wire protocol is framework-agnostic.

### Boundary mapping (direct recommendation)

| Ensemble Node boundary | Best-fit protocol | Verdict |
|---|---|---|
| Web UI ↔ agent/node | **AG-UI** | Purpose-built streaming/state-sync/HITL-interrupt backbone for exactly this edge |
| Agent ↔ agent (cross-human/cross-vendor group chat) | **A2A** | Strong for opaque task delegation + real auth/streaming, but pairwise by design — you add group semantics |
| Agent ↔ tools | **MCP** | De facto standard; build for version negotiation given the recent breaking change |
| App/daemon ↔ local coding-agent CLI | **ACP** | Exactly its design target, already wired into Gemini CLI/Claude Code/Codex/Copilot CLI; remote-driving still WIP upstream |

**Pros/cons distilled for "humans + multiple streaming per-human bots in one room":**
- **Best turnkey match for the AI-streaming-specific need**: **Ably AI Transport** (purpose-built, but positioned as an alternative to its own Chat SDK rather than unified with it) or **Convex's Agent component** (threads natively mix human + multiple named agents, streaming write = persistence write).
- **Best if you want one bundled Postgres-backed stack with least new infra to operate**: **Supabase Realtime**.
- **Cheapest at scale / most control**: **Cloudflare Durable Objects + PartyServer** — but budget DIY engineering time for presence/typing/chat-specific UX since none of that is bundled, and note the hosted PartyKit product itself is being discontinued this week.
- **Avoid or budget around hard room-size ceilings**: Liveblocks (10–100 connections/room) and Pusher (100 presence members/channel) both impose caps that a busy multi-human, multi-bot room could hit.
- **Matrix** is the best fit only if decentralization/federation is a hard requirement — its polling-based transport and per-edit-event streaming convention are a meaningfully worse match for token-by-token fan-out than any purpose-built SaaS option here.
